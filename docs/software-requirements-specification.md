## 1. 文档说明

### 1.1 编写目的

本文档用于明确轻量级外卖服务平台的业务目标、系统边界、参与者、功能需求、业务规则、非功能需求、数据约束、接口约束和验收标准，为以下工作提供统一依据：

1. 小组进行需求分析和架构设计；
2. 按照 TDD 流程设计测试用例和实现业务代码；
3. 前后端分离开发及接口联调；
4. 需求变更后的影响分析、回归测试和代码重构；
5. 组间交叉验收和项目答辩。

本文档以“业务目标 → 用例 → 业务规则 → 接口/数据 → 测试 → 验收”为主要追踪链路，后续需求变更必须同步更新受影响的内容。

### 1.2 项目背景

本项目是 26271 学期软件工程综合实践项目，项目周期为 2026-08-31 至 2026-09-20，共 3 周。系统参考饿了么等外卖平台的核心业务流程，为普通用户提供店铺和商品浏览、购物车管理、订单创建及订单查询能力，为商家提供店铺、商品分类、商品和库存管理能力。

项目不以堆叠复杂功能为目标，而以以下软件工程能力为重点：

- 测试驱动开发（TDD）的红—绿—重构流程；
- 前后端分离及清晰的接口契约；
- Controller、Service、Mapper/Dao、Entity 分层；
- 需求变化下的低耦合和可扩展架构；
- Git 过程证据和小组协作；
- 组间客观、可重复的交叉验收。

### 1.3 项目目标

#### 1.3.1 业务目标

1. 普通用户能够注册、登录并维护个人信息；
2. 普通用户能够浏览店铺、查看商品并完成购物车操作；
3. 普通用户能够维护收货地址，根据购物车创建带地址和备注的订单；
4. 普通用户能够完成模拟支付、取消订单、查询退款状态和确认收货；
5. 商家能够注册并管理自己的店铺资料、店铺地址和营业状态；
6. 商家能够维护商品分类、主图、规格、价格、上下架状态和库存；
7. 商家能够查询店铺订单并推进制作和配送状态；
8. 系统能够对身份、权限、资源归属、状态迁移、价格、库存和幂等性进行校验。

#### 1.3.2 工程目标

1. 所有核心接口和核心业务方法遵循测试优先开发；
2. 核心业务接口测试覆盖率达到 100%，关键业务方法覆盖率不低于 90%；
3. 后端采用标准四层架构，避免 Controller 与数据库或复杂业务规则直接耦合；
4. 接口统一使用 `/api/v1` 版本前缀和结构化响应体；
5. 第二阶段新增需求可以通过扩展现有模块完成，不进行大面积重构；
6. 留存测试类、测试日志、覆盖率报告、Git 提交记录和需求变更记录。

## 2. 系统愿景与范围

### 2.1 系统愿景

为普通用户提供店铺浏览、规格选择、地址管理、购物车、下单、模拟支付和确认收货服务；为商家提供店铺地址、商品、规格库存和订单履约管理能力，形成一个轻量级、可测试、可扩展的外卖服务平台。

### 2.2 系统边界

#### 2.2.1 系统内

- 用户注册、登录和个人信息管理；
- 商家注册和店铺状态管理；
- 店铺列表、详情和营业状态展示；
- 商品分类、商品信息、价格和库存管理；
- 单商品主图上传、替换和删除；
- 单规格维度的多 SKU、SKU 价格、库存和上下架管理；
- 用户收货地址簿和店铺经营地址管理；
- 购物车增删改查；
- 带收货地址快照和备注的订单创建、查询和状态展示；
- 模拟支付、商家开始制作和配送、用户确认收货；
- 待支付订单取消，以及已支付未配送订单取消后的同步模拟退款；
- 身份认证、权限控制、参数校验和统一异常处理；
- 自动化测试、回归测试和覆盖率统计。

#### 2.2.2 系统外

以下能力不属于本版本范围：

- 真实支付渠道和支付回调；
- 骑手管理、配送路径规划和实时配送调度；
- 地图选点、距离计算和配送范围判断；
- 多规格组笛卡尔组合、加料和套餐组合；
- 配送中或已完成订单的售后、争议和部分退款；
- 商家结算、平台抽成和财务对账；
- 复杂推荐、搜索排序算法和个性化画像；
- 即时通讯、客服和实时聊天；
- 真实短信、邮件或第三方身份认证服务。

#### 2.2.3 后续可扩展范围

架构应为以下功能预留扩展空间，但本版本不强制实现：

- 优惠券、满减和会员折扣；
- 用户评价和商家评分；
- 真实支付、异步退款和完整售后；
- 骑手信息和实时配送轨迹；
- 管理员和平台运营后台。

#### 2.2.4 V1.2 已冻结业务决策

1. 每个商品只支持一张主图；下架草稿可无图，上架前必须有合法主图。
2. 商品采用单一规格维度的多 SKU 模型；无差异化规格时创建“默认规格”，价格、库存、状态和版本归属于 SKU。
3. 用户维护多个收货地址且最多一个默认地址；首个地址自动设为默认地址，删除默认地址后不自动指定其他地址；商家维护店铺经营地址，不建立商家个人地址簿。
4. 每个订单只包含一个店铺的购物车项，创建时保存用户地址、店铺地址、商品和 SKU 快照。
5. 订单备注可选，纯空白内容按无备注处理，去除首尾空格后最长 200 个字符，订单创建后不可修改。
6. SKU 库存在创建订单时扣减，加入购物车和模拟支付时不扣减；取消订单时最多恢复一次。
7. 支付和退款均为平台内部模拟，不连接真实渠道；模拟支付使用幂等键，模拟退款与取消操作同步完成。
8. 用户可取消 `PENDING_PAYMENT`、`PAID` 和 `PREPARING` 订单；后两种状态取消时全额退款；配送中及之后不允许普通取消。
9. 商家负责 `PAID -> PREPARING -> DELIVERING`，用户负责 `DELIVERING -> COMPLETED`；商家不能代替用户确认收货。
10. 配送中或已完成订单的售后、部分退款、地图配送和多规格组合不属于本版本。

### 2.3 系统整体流程

```text
普通用户注册/登录
        ↓
浏览店铺列表与店铺详情
        ↓
查看商品分类、商品详情和库存
        ↓
选择商品规格并加入购物车
        ↓
选择收货地址并填写可选备注
        ↓
创建订单
        ↓
模拟支付并等待商家制作、配送
        ↓
确认收货或按规则取消并查看退款结果
```

商家侧流程：

```text
商家注册/登录
        ↓
创建或进入自己的店铺
        ↓
维护店铺地址及营业状态
        ↓
维护商品分类、主图和规格
        ↓
维护 SKU 价格、库存和上下架状态
        ↓
查看订单并推进制作和配送状态
```

## 3. 参与者分析

### 3.1 参与者定义

| 参与者     | 类型         | 主要目标                             | 触发的主要用例                     |
| ---------- | ------------ | ------------------------------------ | ---------------------------------- |
| 普通用户   | 主要参与者   | 浏览商品、管理购物车、创建并查询订单 | 注册、登录、浏览店铺、购物车、订单 |
| 商家       | 主要参与者   | 管理店铺、分类、商品和库存           | 注册商家、管理店铺、管理商品       |
| 系统       | 系统参与者   | 执行身份、状态、库存和业务规则校验   | 所有受规则约束的用例               |
| 前端客户端 | 外部交互系统 | 展示页面并调用后端接口               | 所有前后端交互用例                 |
| 数据库     | 外部支持系统 | 保存和查询业务数据                   | 用户、店铺、商品、购物车、订单     |
| 测试工具   | 外部支持工具 | 执行自动化测试、接口测试和回归测试   | TDD 测试和交叉验收                 |

### 3.2 参与者边界

- 普通用户只能操作本人拥有的个人信息、购物车和订单；
- 商家只能操作自己注册或拥有的店铺、商品分类、商品和相关订单；
- 系统负责最终业务规则校验，前端校验不能替代后端校验；
- 数据库不直接向客户端暴露；
- 前端客户端不直接访问数据库，只能通过后端接口获取数据；
- 测试工具用于验证系统，不参与正式业务数据的权限绕过。

### 4.3 用例关系说明

#### 4.3.1 创建订单包含的业务步骤

`UC-ORDER-001 创建订单` 必须包含以下步骤：

```text
验证登录状态
    ↓
读取购物车
    ↓
验证收货地址归属和完整性
    ↓
验证店铺状态
    ↓
验证商品及 SKU 状态
    ↓
验证 SKU 版本和库存
    ↓
计算金额
    ↓
创建订单、地址快照与明细快照
    ↓
扣减库存
    ↓
清理购物车
```

#### 4.3.2 加入购物车与商品浏览的关系

用户只有在能够识别一个有效商品及可购买 SKU，并且商品、SKU 和店铺均处于允许购买的状态时，才能执行加入购物车。商品详情或商品列表是加入购物车的前置业务信息来源，但不能将前端页面的显示状态作为最终授权依据。

#### 4.3.3 取消订单与订单状态的关系

取消订单是对订单状态的业务变更，不等同于删除订单资源，因此使用：

```text
POST /api/v1/orders/{orderId}/cancel
```

系统必须根据订单、支付和退款状态判断是否允许取消。`PENDING_PAYMENT` 订单取消时不退款；`PAID` 或 `PREPARING` 订单取消时必须恢复库存并完成同步模拟退款；`DELIVERING`、`COMPLETED` 和 `CANCELLED` 订单不允许普通取消。

#### 4.3.4 支付与履约关系

模拟支付、商家履约和用户确认收货必须遵守以下顺序：

```text
创建订单（PENDING_PAYMENT）
        ↓ 用户模拟支付
已支付（PAID）
        ↓ 商家开始制作
制作中（PREPARING）
        ↓ 商家开始配送
配送中（DELIVERING）
        ↓ 用户确认收货
已完成（COMPLETED）
```

系统不得接受跳过前置状态的操作。真实骑手配送不在本版本范围内，“开始配送”仅表示商家将订单推进到模拟配送阶段。

### 5.2 用户模块

#### FR-USER-001 注册账号

系统应允许未注册用户使用账号和密码创建普通用户账号。

**参与者**：普通用户。

**前置条件**：用户未登录或当前没有可用账号。

**基本事件流**：

1. 用户输入账号、密码和确认密码；
2. 系统校验必填项和格式；
3. 系统查询账号是否已经存在；
4. 系统以安全方式保存用户信息；
5. 系统返回注册成功结果。

**备选/异常流**：

- 账号为空：返回参数错误；
- 密码为空：返回参数错误；
- 两次密码不一致：返回密码不一致；
- 账号已存在：返回资源冲突；
- 密码不符合长度或复杂度要求：返回参数错误；
- 数据库保存失败：不返回成功，不产生不完整用户记录。

**后置条件**：成功时生成一个状态正常的用户账号；失败时数据库不新增无效账号。

**关联规则**：`BR-USER-001`、`BR-USER-002`。

**关联接口**：`POST /api/v1/users`。

**验收条件**：合法账号可以注册；重复账号不能注册；失败场景有明确错误提示；密码不以明文形式返回或展示。

#### FR-USER-002 用户登录

系统应允许状态正常的普通用户使用正确凭据登录。

**参与者**：普通用户。

**前置条件**：账号已经注册。

**基本事件流**：

1. 用户输入账号和密码；
2. 系统查询账号；
3. 系统校验密码；
4. 系统校验账号状态；
5. 系统生成登录凭证或会话标识；
6. 系统返回用户基本身份信息。

**备选/异常流**：

- 账号不存在：登录失败；
- 密码错误：登录失败；
- 账号被禁用：拒绝登录；
- 账号或密码为空：返回参数错误；
- 多次失败登录：本版本至少记录失败，不强制实现验证码或锁定策略。

**后置条件**：成功时客户端可以携带凭证访问受保护资源；失败时不得创建有效登录会话。

**关联接口**：`POST /api/v1/users/login`。

**验收条件**：正确凭据登录成功；错误凭据和禁用账号登录失败；未认证请求不能访问受保护资源。

#### FR-MERCHANT-002 商家登录

系统应允许状态正常的商家使用正确凭据登录。

**参与者**：商家。

**前置条件**：商家账号已经注册。

**基本事件流**：

1. 商家输入账号和密码；
2. 系统查询商家账号；
3. 系统校验密码；
4. 系统校验商家状态；
5. 系统生成登录凭证或会话标识；
6. 系统返回商家基本身份信息。

**备选/异常流**：

- 账号不存在：登录失败；
- 密码错误：登录失败；
- 商家被暂停经营：拒绝登录；
- 账号或密码为空：返回参数错误。

**后置条件**：成功时客户端可以携带凭证访问商家受保护资源；失败时不得创建有效登录会话。

**关联接口**：`POST /api/v1/merchants/login`。

**验收条件**：正确凭据登录成功；错误凭据和暂停经营商家登录失败；未认证请求不能访问商家受保护资源。

#### FR-USER-003 查询个人信息

登录用户可以查询自己的账号、联系方式和账号状态等非敏感信息。

**接口**：`GET /api/v1/users/me`。

**规则**：只能返回当前登录用户信息，不返回密码；未登录时返回未认证错误。

#### FR-USER-004 修改个人信息

登录用户可以修改允许变更的个人资料。

**接口**：`PATCH /api/v1/users/me`。

**规则**：只能修改本人资料；账号唯一标识默认不允许随意修改；提交空值或非法格式时更新失败；更新失败时不得保存部分无效数据。

#### FR-ADDRESS-001 管理收货地址

登录用户可以新增、分页或列表查询、修改、删除自己的收货地址，并设置一个默认地址。

**核心字段**：收货人、手机号、区域、详细地址、是否默认。

**基本事件流**：

1. 用户提交地址信息；
2. 系统校验身份、字段长度和手机号格式；
3. 系统保存地址；若这是用户的首个有效地址，则自动设为默认地址；
4. 设置新默认地址时，系统在同一事务内取消该用户原默认地址；
5. 系统返回保存后的地址。

**异常流**：地址不存在、地址不属于当前用户、必填字段缺失、手机号格式错误、重复删除或数据库失败。

**后置条件**：成功时地址簿更新且最多只有一个默认地址；失败时不得产生部分更新。删除当前默认地址后不自动指定其他地址，用户下单时仍须显式选择有效地址。删除地址只影响地址簿，不修改历史订单的地址快照。

**验收条件**：用户只能管理本人地址；默认地址唯一；删除或修改地址后历史订单收货信息保持不变。

### 5.3 商家和店铺模块

#### FR-MERCHANT-001 注册商家

系统应允许未注册经营者创建商家账号。

**接口建议**：`POST /api/v1/merchants`。

**异常场景**：重复账号、必填字段缺失、联系方式格式错误、密码不符合要求。

**验收条件**：注册成功后商家可登录；商家资料与普通用户资料权限隔离。

#### FR-MERCHANT-003 查询商家资料

登录商家可以查询自己的商家账号、名称、联系方式和状态等非敏感信息。

**接口**：`GET /api/v1/merchants/me`。

**规则**：只能返回当前登录商家信息，不返回密码；未登录或无效凭证时返回未认证错误。

#### FR-MERCHANT-004 修改商家资料

登录商家可以修改允许变更的商家资料。

**接口**：`PATCH /api/v1/merchants/me`。

**规则**：只能修改本人商家资料；账号唯一标识默认不允许随意修改；提交空值或非法格式时更新失败。

#### FR-SHOP-001 创建店铺

登录商家可以创建属于自己的店铺。

**前置条件**：商家已登录并具有创建店铺权限。

**基本事件流**：

1. 商家提交店铺名称、简介等信息；
2. 系统校验商家身份和字段格式；
3. 系统检查店铺名称和归属关系；
4. 系统创建店铺；
5. 系统返回店铺信息。

**异常流**：商家未登录、无权创建、名称为空、重复创建不符合规则、数据库保存失败。

**初始状态**：新建店铺固定为 `CLOSED`（已关闭），完善经营地址后方可切换为 `OPEN`（营业中）。

**接口**：`POST /api/v1/shops`。

#### FR-SHOP-002 修改店铺状态

商家可以将自己店铺的状态设置为营业、关店或临时闭店。

**接口建议**：`PATCH /api/v1/shops/{shopId}`。

**规则**：

- 商家不能修改其他商家的店铺；
- 状态必须是系统允许的枚举值；
- 关店或临时闭店后不能创建新的订单；
- 状态变更不能删除店铺或历史订单。

#### FR-SHOP-003 浏览店铺列表

普通用户可以分页查询店铺列表，并查看店铺名称、简介和营业状态。

**接口**：`GET /api/v1/shops`。

**查询参数**：`page`、`pageSize`、`keyword`、`status`、`sortBy`、`sortOrder`。

**边界规则**：页码从 1 开始；页大小必须为正数且不超过系统上限；无匹配结果返回空列表而非错误。

#### FR-SHOP-004 查看店铺详情

普通用户可以查看指定店铺的详细信息和当前状态。

**接口**：`GET /api/v1/shops/{shopId}`。

**异常流**：店铺不存在返回资源不存在；店铺已逻辑删除时不作为可用店铺返回。

#### FR-SHOP-005 维护店铺地址

商家可以为自己的店铺维护一个经营地址和联系电话。

**核心字段**：区域、详细地址、联系电话。本版本不要求经纬度、地图选点和配送范围计算。

**规则**：商家只能修改自己店铺的地址；店铺进入营业状态前必须具有完整经营地址；地址修改不改变历史订单中的店铺地址快照。

**异常流**：店铺不存在、无店铺权限、地址字段缺失或联系方式格式错误。

**验收条件**：有效地址可保存并在店铺详情中按权限展示；无地址店铺不能切换为营业状态。

### 5.4 商品模块

#### FR-PRODUCT-001 管理商品分类

商家可以在自己的店铺中新增、修改、查询和逻辑删除商品分类。

**接口建议**：

```text
POST   /api/v1/shops/{shopId}/categories
GET    /api/v1/shops/{shopId}/categories
PATCH  /api/v1/categories/{categoryId}
DELETE /api/v1/categories/{categoryId}
```

**规则**：分类必须归属于当前商家店铺；分类名称不能为空；存在有效商品的分类不能被无条件物理删除。

#### FR-PRODUCT-002 新增商品

商家可以向自己的店铺和商品分类中新增商品。

**基本字段**：商品名称、分类、描述、主图和状态；实际销售价格、库存和可售状态由 SKU 维护。

**基本事件流**：

1. 商家提交商品信息；
2. 系统校验商家和店铺归属；
3. 系统校验商品分类；
4. 系统校验商品信息、主图引用和至少一个 SKU；
5. 系统保存商品；
6. 系统返回商品信息。

**规则**：创建商品时必须同时提交至少一个 SKU 并原子保存；无差异化规格时使用“默认规格”；SKU 价格必须大于 0、库存必须大于或等于 0；新商品和新 SKU 默认下架；商品或 SKU 任一为下架状态时均不能购买。主图允许在下架草稿阶段为空，但商品上架前必须具有合法主图。

**接口**：`POST /api/v1/products`。

#### FR-PRODUCT-003 修改商品

商家可以局部修改自己商品的名称、描述、分类、主图等允许修改的字段，并通过 SKU 功能维护销售价格和库存。

**接口**：`PATCH /api/v1/products/{productId}`。

**规则**：修改商品时必须重新校验所有被修改字段；不能修改其他商家的商品；商品或 SKU 修改不得改变历史订单中的名称、规格和成交价格快照。

#### FR-PRODUCT-004 管理商品状态和库存

商家可以上架、下架商品，并调整 SKU 的状态和库存。

**接口建议**：

```text
PATCH /api/v1/products/{productId}
```

**规则**：库存归属于 SKU 且不能小于 0；SKU 库存为 0 时不得被当作有货规格；下架商品和 SKU 可以保留历史数据，但不能加入购物车或创建新订单。

#### FR-PRODUCT-005 浏览商品

普通用户可以查看指定店铺的商品分类、商品列表和商品详情。

**接口建议**：

```text
GET /api/v1/shops/{shopId}/products
GET /api/v1/products/{productId}
```

**查询参数**：`categoryId`、`keyword`、`page`、`pageSize`、`sortBy`、`sortOrder`。

**规则**：普通用户默认只能看到上架商品和可售 SKU；商品列表展示主图、起始价格和库存状态，商品详情展示全部可售规格；商品不存在或不属于指定店铺时返回错误；无主图时展示统一占位图。

#### FR-PRODUCT-006 管理商品主图

商家可以在新增或编辑商品时上传、替换或删除一张商品主图。

**规则**：仅支持 JPG、PNG 和 WebP；单文件不超过 5 MB；文件内容和类型均须由服务端校验；上传成功后返回可持久引用的文件标识或 URL；下架草稿商品可暂时无主图，但商品上架前必须关联一张合法主图；商品删除或换图后的孤立文件按文件生命周期策略清理，但仍被历史订单快照引用的文件不得删除，且其快照 URL 必须持续可访问。

**异常流**：文件为空、格式不支持、超过大小限制、内容与扩展名不符、上传失败或引用不存在。

**验收条件**：合法图片可预览并关联商品；非法图片被拒绝；接口和数据库不得保存 Base64 正文或客户端本地绝对路径。

#### FR-PRODUCT-007 管理商品规格

商家可以为商品维护单一规格维度下的多个 SKU，例如“小份”“大份”；本版本不支持尺寸、温度、加料等多个规格组的组合计算。

**SKU 字段**：SKU ID、商品 ID、规格名称、价格、库存、状态、版本号。

**规则**：同一商品内规格名称唯一；每个商品至少有一个 SKU；无差异化规格的商品使用“默认规格”；SKU 独立维护价格、库存、状态和版本；已被购物车或订单引用的 SKU 不得物理删除；并发更新必须校验版本号。

**验收条件**：商家可以新增、修改和上下架本人店铺商品的 SKU；用户必须选择有效 SKU 才能加入购物车；SKU 修改不影响历史订单快照。

### 5.5 购物车模块

#### FR-CART-001 加入购物车

登录用户可以将可购买商品加入购物车。

**前置条件**：用户已登录；商品和所选 SKU 存在、属于有效店铺、均处于上架状态且 SKU 库存充足。

**基本事件流**：

1. 用户选择商品、SKU 和数量；
2. 系统验证用户身份；
3. 系统读取商品、SKU 和店铺状态；
4. 系统校验数量、SKU 状态、版本和库存；
5. 若购物车已有同一 SKU 则增加数量，否则创建购物车项；
6. 系统返回购物车项。

**异常流**：未登录、商品或 SKU 不存在、商品或 SKU 下架、店铺不可营业、数量非正整数、数量超过 SKU 库存。

**接口**：`POST /api/v1/cart-items`。

#### FR-CART-002 查询购物车

登录用户可以查询自己的购物车及商品小计。

**接口**：`GET /api/v1/cart-items`。

**规则**：只返回当前用户购物车；展示商品主图、SKU 名称及最新价格和状态，但不擅自修改订单历史；购物车为空返回空列表。

#### FR-CART-003 修改购物车数量

用户可以调整自己购物车项的数量。

**接口**：`PATCH /api/v1/cart-items/{itemId}`。

**规则**：数量必须为正整数且不能超过当前 SKU 库存；购物车项不存在或不属于当前用户时不能修改；若商品或 SKU 已下架、版本已变化或店铺不可营业，系统应返回明确冲突而不是默默提交。

#### FR-CART-004 删除购物车商品

用户可以删除自己的购物车项。

**接口**：`DELETE /api/v1/cart-items/{itemId}`。

**规则**：删除购物车项不影响 SKU 库存和历史订单；重复删除已不存在项目时返回明确结果，不得删除其他用户项目。

### 5.6 订单模块

#### FR-ORDER-001 创建订单

用户可以根据有效购物车内容创建订单。该用例是本项目的核心业务用例，必须重点进行单元测试、接口测试和事务测试。

**参与者**：普通用户；系统、数据库为支持参与者。

**触发条件**：用户在购物车页面提交订单。

**前置条件**：

- 用户已登录；
- 购物车不为空；
- 已选择一条有效且属于当前用户的收货地址；
- 购物车商品满足店铺归属规则；
- 店铺处于营业状态；
- 商品和 SKU 处于上架状态；
- 每个 SKU 版本与用户确认时一致且库存满足购买数量；
- 订单备注为空或不超过 200 个字符。

**成功后置条件**：

- 创建订单主记录；
- 创建订单明细；
- 保存用户收货地址和店铺地址快照；
- 保存下单时的商品名称、规格名称、主图引用、成交单价和数量；
- 保存去除首尾空格后的可选订单备注，纯空白内容归一化为无备注；
- 计算并保存订单总金额；
- 扣减 SKU 库存；
- 清理已提交的购物车项；
- 返回订单编号和订单摘要。

**失败后置条件**：

- 不生成不完整订单；
- 不错误扣减库存；
- 不错误删除购物车项；
- 返回可理解的业务错误；
- 数据库异常时事务回滚。

**基本事件流**：

1. 用户提交购物车项引用、SKU 版本、收货地址 ID 和可选备注；
2. 系统验证登录状态；
3. 系统校验地址属于当前用户并读取地址快照；
4. 系统读取购物车、商品、SKU 和店铺信息；
5. 系统检查店铺营业状态及店铺地址完整性；
6. 系统检查商品和 SKU 是否上架；
7. 系统检查 SKU 版本和库存；
8. 系统按照 SKU 当前有效价格计算金额；
9. 系统创建订单、地址快照和订单明细快照；
10. 系统扣减 SKU 库存；
11. 系统删除已购买的购物车记录；
12. 系统提交事务并返回 `PENDING_PAYMENT` 订单。

**备选事件流**：

- SKU 价格发生变化：提示用户确认最新价格，本版本不得无提示地使用客户端旧价格；
- SKU 版本发生变化：整单失败并返回当前 SKU 信息供用户重新确认；
- 商品部分缺货：默认整笔订单创建失败并指出缺货商品；
- 购物车包含多个店铺商品：默认拒绝提交并提示按店铺分别下单；若后续改为自动拆单，必须新增需求和测试；
- 店铺临时闭店：创建失败并提示店铺暂不可下单；
- 地址不存在或不属于当前用户：创建失败且不得泄漏其他用户地址；
- 备注为空或仅含空白：按无备注创建订单；
- 备注超过 200 字符：创建失败且不得截断后静默保存；
- 重复提交：使用请求幂等策略或业务校验避免生成重复订单。

**异常事件流**：

- 用户未登录：返回 401；
- 购物车为空：返回 400；
- 商品或店铺不存在：返回 404；
- 库存不足：返回 409；
- 数据库写入失败：事务回滚并返回服务器错误；
- 网络异常：客户端不得将未确认的请求显示为已成功。

**关联规则**：`BR-ORDER-001` 至 `BR-ORDER-008`。

**接口**：`POST /api/v1/orders`。

**验收条件**：合法购物车、地址和备注可以成功下单；所有非法状态被拒绝；失败后 SKU 库存和购物车保持正确；订单保留地址、店铺、商品和规格快照；相关测试全部通过。

#### FR-ORDER-002 查询订单列表

登录用户可以分页查询自己的订单列表。

**接口**：`GET /api/v1/orders`。

**查询参数**：`status`、`page`、`pageSize`、`sortBy`、`sortOrder`。

**规则**：只能返回当前用户订单；默认按创建时间倒序；无订单返回空列表；分页参数必须校验。

#### FR-ORDER-003 查看订单详情

登录用户可以查看自己的订单主信息、订单明细、总金额、店铺、收货地址快照、备注、订单状态、支付状态和退款状态。

**接口**：`GET /api/v1/orders/{orderId}`。

**规则**：订单不存在返回 404；订单属于其他用户时不得泄漏详情，可统一返回无权访问或资源不存在；历史订单使用下单时的地址、商品名称、规格名称和成交单价快照。

#### FR-ORDER-004 取消订单

用户可以在允许取消的状态下取消自己的订单。

**接口**：`POST /api/v1/orders/{orderId}/cancel`。

**基本事件流**：

1. 用户提交取消请求和可选取消原因；
2. 系统验证用户身份和订单归属；
3. 系统检查订单当前状态；
4. 系统判断是否需要退款；
5. 系统将订单状态修改为已取消并恢复 SKU 库存一次；
6. 已支付订单在同一事务内创建唯一退款记录，并同步完成模拟退款；
7. 系统返回订单、支付和退款结果。

**异常流**：订单不存在、订单属于其他用户、订单已完成、订单已取消、订单处于配送中或其他不可取消状态、退款重复、状态并发冲突。

**规则**：取消原因可选，去除首尾空格后最长 200 个字符。`PENDING_PAYMENT`、`PAID` 和 `PREPARING` 允许用户取消；`PENDING_PAYMENT` 不产生退款；`PAID` 和 `PREPARING` 必须全额模拟退款；`DELIVERING`、`COMPLETED` 和 `CANCELLED` 不允许普通取消。取消不删除订单及明细；库存只能恢复一次；同一支付记录只能成功退款一次。已支付订单退款后支付状态仍为 `PAID`，退款结果由退款状态单独表达。

#### FR-PAYMENT-001 模拟支付

用户可以在本人 `PENDING_PAYMENT` 订单详情中执行模拟支付。

**基本事件流**：系统校验身份、订单归属和状态，创建成功支付记录，将支付状态改为 `PAID`、订单状态改为 `PAID`，并返回最新订单和支付结果。

**异常流**：订单不存在、无权访问、订单状态不允许、相同幂等键对应不同请求、重复支付或数据库失败。

**规则**：模拟支付不连接真实支付渠道、不采集银行卡等支付凭据；请求必须使用幂等键；相同订单成功支付后不得生成第二条成功支付记录；失败时订单保持 `PENDING_PAYMENT` 和 `UNPAID`。

**验收条件**：待支付订单可成功模拟支付；重复请求返回首次结果；取消或已支付订单不能再次支付；支付记录与订单状态保持一致。

#### FR-ORDER-005 确认收货

用户可以对本人处于 `DELIVERING` 状态的订单确认收货。

**规则**：确认收货后订单进入 `COMPLETED`；其他状态不得确认；重复请求必须幂等；确认完成后不能再普通取消。

**验收条件**：只有订单所有者能确认收货，且仅允许 `DELIVERING -> COMPLETED`。

#### FR-REFUND-001 查询模拟退款结果

用户可以在被取消的已支付订单详情中查看退款状态、退款金额和退款完成时间。

**规则**：本版本采用同步模拟退款，退款记录按 `REFUNDING -> REFUNDED` 在一次业务操作中完成；退款金额等于订单实付金额；不支持部分退款和手工重复退款入口。

**验收条件**：已支付订单成功取消后具有唯一的全额退款记录；待支付订单取消后不生成退款记录；退款失败时整个取消事务回滚。

### 5.7 商家订单模块

#### FR-MERCHANT-ORDER-001 查看店铺订单列表

商家可以分页查询自己店铺下的订单列表。

**接口**：`GET /api/v1/merchant/orders`。

**规则**：只能返回当前商家店铺下的订单；可按店铺、状态和分页参数查询；无订单返回空列表。

**验收条件**：合法状态可逐步推进；越权、跳转状态和并发冲突均被拒绝且订单保持原状态。

### 6.7 状态模型

#### 用户状态

```text
ACTIVE（正常，注册初始状态）
  └──有权限的管理操作──> DISABLED（禁用）
DISABLED
  └──有权限的管理操作──> ACTIVE
```

普通用户不能自行修改账号状态；本版本不提供面向普通用户或商家的账号状态管理入口。

#### 商家状态

```text
ACTIVE（正常，注册初始状态）
  └──有权限的管理操作──> SUSPENDED（暂停经营权限）
SUSPENDED
  └──有权限的管理操作──> ACTIVE
```

暂停经营的商家不能登录或执行店铺、商品和订单管理操作，但不得删除其店铺和历史业务数据；本版本不提供面向普通用户或商家的商家状态管理入口。

#### 店铺状态

```text
CLOSED（关店，新建初始状态） ─────────────→ OPEN（营业）
OPEN ────────────────────────────────────→ CLOSED
OPEN ────────────────────────────────────→ TEMPORARILY_CLOSED（临时闭店）
TEMPORARILY_CLOSED ──────────────────────→ OPEN
TEMPORARILY_CLOSED ──────────────────────→ CLOSED
```

`CLOSED -> OPEN` 和 `TEMPORARILY_CLOSED -> OPEN` 前必须重新校验店铺经营地址完整性。

#### 商品与 SKU 状态

```text
OFF_SALE（下架，新建初始状态） ─────────→ ON_SALE（上架）
ON_SALE ───────────────────────────────→ OFF_SALE
```

商品和 SKU 分别维护上述状态；商品上架前必须具有合法主图和至少一个 SKU，SKU 上架前必须具有合法价格和非负库存。只有商品和所选 SKU 均为 `ON_SALE` 且 SKU 库存大于 0 时才可购买。

#### 订单状态

订单创建成功后的初始状态固定为 `PENDING_PAYMENT`，并且必须支持以下迁移：

```text
PENDING_PAYMENT --用户模拟支付--> PAID
PAID -----------商家开始制作--> PREPARING
PREPARING ------商家开始配送--> DELIVERING
DELIVERING ------用户确认收货--> COMPLETED

PENDING_PAYMENT ------用户取消--> CANCELLED
PAID -----------------用户取消--> CANCELLED + 全额模拟退款
PREPARING ------------用户取消--> CANCELLED + 全额模拟退款
```

`DELIVERING`、`COMPLETED` 和 `CANCELLED` 不允许普通取消；禁止跳过状态、逆向迁移或由商家代替用户确认收货。

#### 支付状态

```text
UNPAID（订单初始状态） --模拟支付成功--> PAID
```

模拟支付失败时保持 `UNPAID`。一个订单最多有一条成功支付记录；订单状态为 `PAID`、`PREPARING`、`DELIVERING` 或 `COMPLETED` 时，支付状态必须为 `PAID`。已支付订单取消并退款后，支付状态仍保留 `PAID`，不得回退为 `UNPAID`。

#### 退款状态

```text
NOT_REFUNDED（订单初始状态） --已支付订单取消--> REFUNDING --同步模拟退款成功--> REFUNDED
```

本版本中 `REFUNDING` 是事务内的中间状态，对外成功结果应为 `REFUNDED`。模拟退款失败时取消操作整体回滚，订单保持取消前状态；待支付订单取消不创建退款记录，其退款状态保持 `NOT_REFUNDED`。

订单、支付和退款状态必须满足以下稳定组合；表外组合不得持久化：

| 订单状态 | 支付状态 | 退款状态 | 说明 |
| -------- | -------- | -------- | ---- |
| `PENDING_PAYMENT` | `UNPAID` | `NOT_REFUNDED` | 待支付 |
| `PAID` / `PREPARING` / `DELIVERING` / `COMPLETED` | `PAID` | `NOT_REFUNDED` | 已支付且未退款 |
| `CANCELLED` | `UNPAID` | `NOT_REFUNDED` | 待支付订单取消 |
| `CANCELLED` | `PAID` | `REFUNDED` | 已支付或制作中订单取消并全额退款 |

`REFUNDING` 只允许在取消事务内部短暂出现，不作为同步接口成功返回后的稳定状态。

## 7. 数据需求

### 7.1 数据对象总览

```text
用户 1 ─── N 订单
用户 1 ─── N 购物车项
用户 1 ─── N 收货地址
商家 1 ─── N 店铺
店铺 1 ─── N 商品分类
店铺 1 ─── N 商品
店铺 1 ─── N 订单
商品分类 1 ─── N 商品
商品 1 ─── N SKU
订单 1 ─── N 订单明细
订单 1 ─── 0..1 支付记录
订单 1 ─── 0..1 退款记录
SKU 1 ─── N 购物车项
商品 1 ─── N 订单明细
SKU 1 ─── N 订单明细
```

### 7.2 用户对象

**含义**：平台登录和权限校验的用户主体。

**核心属性**：用户 ID、账号、密码摘要、昵称、联系方式、状态、创建时间、更新时间。

**约束**：用户 ID 唯一；账号非空且唯一；密码不得明文保存；状态只能取系统定义值。

**生命周期**：注册、正常使用、禁用或逻辑删除。

**访问权限**：用户可读取和修改自己的非敏感信息；商家管理自己的商家资料；其他用户不得读取。

**扩展方向**：头像、用户角色、最后登录时间。

### 7.3 用户地址对象

**含义**：用户下单时可选择的收货地址。

**核心属性**：地址 ID、用户 ID、收货人、手机号、区域、详细地址、默认标记、创建时间、更新时间。

**约束**：必须属于有效用户；必填字段不能为空；同一用户最多一个默认地址；删除采用逻辑删除或等效历史保护策略。

**访问权限**：仅地址所有者可查询和管理；商家只能通过所属订单读取地址快照，不能访问用户地址簿。

### 7.4 商家对象

**含义**：店铺经营主体。

**核心属性**：商家 ID、关联账号、商家名称、联系方式、状态、创建时间。

**约束**：商家必须关联有效账号；商家状态影响店铺管理权限。

**访问权限**：商家只能读取和修改自己的资料；普通用户只能查看必要展示信息。

### 7.5 店铺对象

**含义**：商家提供商品和接收订单的经营主体。

**核心属性**：店铺 ID、商家 ID、店铺名称、简介、经营区域、详细地址、联系电话、状态、创建时间、更新时间。

**约束**：必须关联一个商家；状态必须是营业、关店或临时闭店；逻辑删除后不能作为有效店铺使用。

**扩展方向**：营业时间、店铺图片、起送价、配送费、公告和经纬度。

### 7.6 商品分类对象

**含义**：店铺内组织商品的分类。

**核心属性**：分类 ID、店铺 ID、分类名称、排序号、状态、创建时间。

**约束**：同一店铺内分类名称不得违反唯一性规则；存在商品引用时应优先逻辑删除或阻止删除。

### 7.7 商品对象

**含义**：用户可以浏览和购买的商品。

**核心属性**：商品 ID、店铺 ID、分类 ID、名称、描述、主图引用、上下架状态、创建时间、更新时间。

**约束**：商品必须归属于有效店铺；非空主图引用必须有效且上架商品必须有主图；商品至少关联一个 SKU；历史订单不依赖商品当前名称、图片和状态，订单主图快照 URL 在历史订单保留期间必须可访问。

### 7.8 SKU 对象

**含义**：商品的实际可购买规格。

**核心属性**：SKU ID、商品 ID、规格名称、价格、库存、状态、版本号、创建时间、更新时间。

**约束**：价格大于 0；库存不小于 0；状态为上架或下架；同一商品内规格名称唯一；版本号用于防止并发覆盖。

### 7.9 购物车项对象

**含义**：用户选择但尚未形成订单的商品记录。

**核心属性**：购物车项 ID、用户 ID、SKU ID、数量、用户最后确认的 SKU 版本、创建时间、更新时间。

**约束**：用户、商品和 SKU 必须有效；数量为正整数；同一用户同一 SKU 原则上只保留一个购物车项。

### 7.10 订单对象

**含义**：用户提交购买请求后形成的业务记录。

**核心属性**：订单 ID、订单编号、用户 ID、店铺 ID、总金额、订单备注、用户收货地址快照、店铺地址快照、订单状态、支付状态、退款状态、创建时间、更新时间、取消原因、取消时间和完成时间。

**约束**：订单编号唯一；总金额由服务端计算；订单状态必须遵守状态迁移规则；历史订单不得因商品当前数据变化而改变。

### 7.11 订单明细对象

**含义**：订单中的商品快照和数量记录。

**核心属性**：明细 ID、订单 ID、商品 ID、SKU ID、商品名称快照、规格名称快照、商品主图 URL 快照、成交单价、购买数量、小计。

**约束**：成交单价、商品名称和规格名称在创建订单时写入；小计由服务端计算；订单明细不能脱离订单单独存在。

### 7.12 支付记录对象

**含义**：订单的一次成功模拟支付结果。

**核心属性**：支付记录 ID、订单 ID、支付流水号、支付金额、支付状态、幂等键、支付时间、创建时间。

**约束**：一个订单最多一条成功支付记录；支付金额等于订单应付金额；流水号和幂等键满足唯一性规则。

### 7.13 退款记录对象

**含义**：已支付订单取消时产生的全额模拟退款记录。

**核心属性**：退款记录 ID、订单 ID、支付记录 ID、退款流水号、退款金额、退款状态、幂等键、完成时间、创建时间。

**约束**：一条支付记录最多成功退款一次；退款金额等于实付金额；退款记录不得脱离支付记录存在。

### 7.14 数据一致性要求

- 外键关联数据必须存在或经过明确的逻辑删除处理；
- 创建订单的关键写操作必须在一个事务中完成；
- SKU 库存扣减不能导致库存为负数；
- 订单创建失败时，订单、地址快照、订单明细、SKU 库存和购物车项必须恢复到操作前状态；
- 订单取消、库存恢复、退款记录和状态更新必须保持事务一致性；
- 同一订单取消时库存最多恢复一次，同一支付记录最多退款一次；
- 订单历史金额不随商品后续改价变化；
- 地址簿、店铺地址、商品、SKU 或图片后续变化不得改变订单快照；
- 删除操作默认采用逻辑删除，避免破坏历史业务数据。

## 8. 外部接口与系统接口需求

### 8.1 接口总约定

1. 所有业务接口使用 `/api/v1` 版本前缀；
2. URI 以资源名词为中心，避免 `/createOrder`、`/updateGoods` 等动词型路径；
3. `GET` 只执行查询，不修改数据；
4. `POST` 用于创建资源或执行明确的业务动作；
5. `PUT` 表示全量更新，`PATCH` 表示局部更新；
6. `DELETE` 表示删除或逻辑删除；
7. 分页、过滤和排序使用 Query 参数；
8. 使用标准 HTTP 状态码；
9. 后端不得信任客户端传入的金额、权限、商品状态和库存结果；
10. 创建订单、模拟支付、取消订单、履约推进和确认收货必须定义幂等或防重复执行策略；
11. 文件上传必须校验实际内容、类型、大小和资源归属；
12. 详细字段定义以后续接口文档为准，但不得违反本需求基线。

### 8.2 统一响应结构

```json
{
  "code": 0,
  "msg": "操作成功",
  "data": {}
}
```

成功响应中的 `data` 根据接口返回对象确定；列表接口应包含列表和分页信息。失败响应必须包含稳定的错误码和可理解的提示信息，不能将异常堆栈直接返回给客户端。

### 8.3 状态码约定

| 状态码                    | 使用场景                       |
| ------------------------- | ------------------------------ |
| 200 OK                    | 查询或更新成功                 |
| 201 Created               | 创建资源成功                   |
| 204 No Content            | 删除成功且不返回正文时使用     |
| 400 Bad Request           | 参数格式、缺失或业务请求不合法 |
| 401 Unauthorized          | 未认证或登录凭证无效           |
| 403 Forbidden             | 已认证但没有资源操作权限       |
| 404 Not Found             | 资源不存在                     |
| 409 Conflict              | 资源冲突、库存冲突或状态冲突   |
| 500 Internal Server Error | 未预期的服务端错误             |

### 8.5 分页、过滤和排序

列表接口统一支持需要的 Query 参数：

```text
page=1&pageSize=10&keyword=汉堡&status=OPEN&sortBy=createdAt&sortOrder=desc
```

约束：

- `page` 从 1 开始；
- `pageSize` 大于 0 且不超过统一上限；
- 不认识的排序字段必须拒绝或使用安全的默认字段，不能直接拼接 SQL；
- 过滤条件由具体资源定义；
- 空结果返回成功状态和空列表。

## 9. 非功能需求

### 9.1 性能需求

| 编号         | 需求                                                           |
| ------------ | -------------------------------------------------------------- |
| NFR-PERF-001 | 普通查询接口在本地正常运行环境下平均响应时间目标不超过 2 秒。  |
| NFR-PERF-002 | 列表接口必须使用分页，默认每页 10 条，单页上限由统一配置控制。 |
| NFR-PERF-003 | 订单创建应避免重复读取和无必要的跨层调用。                     |

以上指标用于课程实践验收，不等同于生产环境容量承诺。

### 9.2 安全和权限需求

| 编号        | 需求                                                   |
| ----------- | ------------------------------------------------------ |
| NFR-SEC-001 | 密码不得明文存储、日志输出或接口返回。                 |
| NFR-SEC-002 | 购物车、订单和个人信息接口必须验证身份。               |
| NFR-SEC-003 | 服务端必须校验资源归属，不能只依赖前端隐藏按钮。       |
| NFR-SEC-004 | 用户不能访问其他用户的购物车和订单详情。               |
| NFR-SEC-005 | 商家不能管理其他商家的店铺、商品和库存。               |
| NFR-SEC-006 | 错误响应不得暴露数据库结构、密码、堆栈和内部敏感配置。 |

### 9.3 可维护性和架构需求

- 后端严格划分 Entity、Mapper/Dao、Service、Controller；
- Controller 负责请求接收、参数校验和响应转换，不写复杂业务逻辑；
- Mapper/Dao 只负责数据库操作，不承载跨资源业务规则；
- Service 负责业务规则、事务和需求变化相关的扩展点；
- 使用统一异常处理器，新增业务异常不重复编写 Controller 捕获逻辑；
- 使用统一响应对象，前端不因单个接口格式变化而大面积修改；
- 通用参数校验、状态判断和时间处理应适当封装；
- 前端采用路由分层和组件化，Axios 统一处理请求和响应；
- 命名、注释和目录结构保持一致，避免无意义的过度设计。

### 9.4 可测试性需求

- 所有核心接口必须有测试；
- 核心业务接口覆盖率 100%；
- 关键业务方法覆盖率不低于 90%；
- 测试至少覆盖正常、异常和边界场景；
- 权限、状态迁移、库存一致性和事务回滚必须有测试；
- 每个测试必须包含有效断言；
- 需求变更后必须新增测试并执行原有功能回归测试；
- 测试结果、覆盖率和日志应保存到项目交付材料中。

### 9.5 可用性需求

- 表单提交前进行必要的必填和格式校验；
- 服务端返回的错误信息应能被前端转换为用户可理解的提示；
- 列表为空时显示空数据状态；
- 网络请求失败时显示重试或返回建议；
- 订单提交过程中应避免重复点击造成重复请求；
- 商品下架、缺货和店铺闭店状态应在页面上明确展示。

### 9.6 可扩展性需求

- 接口统一使用 `/api/v1`，破坏性变更时可增加 `/api/v2`；
- 优惠、退款等新资源通过新增资源路径接入，不修改无关旧接口；
- 订单规则、价格计算和库存处理集中在 Service 层；
- 状态值使用统一枚举或常量管理，避免散落字符串；
- 统一异常和响应封装，降低新增模块的接入成本；
- 需求变更优先通过新增用例、规则和服务能力实现，避免大面积重构。

## 10. TDD 开发与测试需求

### 10.1 强制开发流程

项目必须遵循以下顺序：

```text
梳理业务目标和用例
        ↓
明确接口行为和验收条件
        ↓
编写测试用例
        ↓
运行测试并确认失败（Red）
        ↓
编写最少业务代码
        ↓
运行测试并确认通过（Green）
        ↓
重构并保持测试通过（Refactor）
        ↓
提交代码并保留过程证据
```

禁止先完成业务代码再集中补测试，禁止测试没有断言，禁止跳过测试直接提交功能。

### 10.2 测试类型

| 类型                | 目标                           | 主要工具            |
| ------------------- | ------------------------------ | ------------------- |
| Service 单元测试    | 验证核心业务规则和分支         | JUnit 5、Mockito    |
| Controller/API 测试 | 验证 HTTP 方法、状态码和响应体 | MockMvc             |
| Mapper 测试         | 验证数据库查询和持久化行为     | JUnit 5、测试数据库 |

| 回归测试            | 验证变更没有破坏旧功能         | 自动化测试集合      |

### 10.3 测试场景要求

核心用例必须考虑：

- 合法输入和成功结果；
- 缺失参数、格式错误和非法值；
- 空数据、零库存、最大数量和分页边界；
- 未登录、凭证无效和权限不足；
- 资源不存在、资源归属错误和重复资源；
- 店铺状态、商品状态和订单状态冲突；
- SKU 不存在、下架、版本冲突和库存不足；
- 地址不存在、地址归属错误、默认地址并发设置；
- 图片格式、内容、大小和无效引用；
- 无备注、纯空白备注归一化、200 字符边界和超长备注；
- 非法支付、重复支付、非法状态推进和重复确认收货；
- 待支付取消不退款、已支付取消全额退款、重复退款；
- 并发或重复提交导致的库存和订单一致性问题；
- 数据库失败后的事务回滚；
- 需求变更后的新规则和旧功能回归。

## 11. 需求变更与迭代机制

### 11.1 阶段安排

| 阶段   | 时间    | 重点                           |
| ------ | ------- | ------------------------------ |
| 阶段 1 | 第 1 周 | 架构打底、基础功能、TDD 测试   |
| 阶段 2 | 第 2 周 | 图片、SKU、地址、备注和下单链路变更 |
| 阶段 3 | 第 3 周 | 模拟支付、履约退款、完整回归和验收 |

### 11.2 变更处理流程

V1.2 已确定商品图片与 SKU、地址与备注、模拟支付和履约退款需求。具体实现仍必须执行以下变更流程：

1. 记录原始需求、新需求和变更原因；
2. 识别受影响的参与者和用例；
3. 识别受影响的业务规则、接口、数据对象和页面；
4. 先新增或修改测试用例；
5. 运行测试，确认新需求测试失败；
6. 在现有分层架构中实现变更；
7. 执行新增测试和原有功能回归测试；
8. 检查是否出现重复代码、跨层耦合或大面积重构；
9. 更新本说明书、接口文档、测试报告和变更记录；
10. 由小组完成变更验收并保留解释材料。

## 12. 交付与验收标准

### 12.1 功能验收

- 用户、商家、店铺、商品与 SKU、地址、购物车、订单、模拟支付和退款功能均可按照用例完成；
- 正常流程可以得到正确结果；
- 异常流程返回明确错误；
- 边界场景不会造成非法数据；
- 用户和商家权限边界有效；
- 订单失败时 SKU 库存和购物车保持一致；
- 订单地址、店铺、商品和规格快照不受源数据后续修改影响；
- 支付、履约、取消、退款和确认收货严格遵守状态机。

### 12.2 REST 接口验收

- 接口统一使用 `/api/v1`；
- URI 以资源名词为中心；
- HTTP 方法语义基本正确；
- 支付、取消、履约推进和确认收货等业务动作使用明确的动作型子路径；
- 状态码和统一响应体符合本说明书；
- 分页、过滤、排序使用 Query 参数；
- 接口参数和错误场景有文档说明。

### 12.3 TDD 验收

- 测试用例先于对应业务实现提交；
- 测试包含有效断言；
- 正常、异常、边界和权限场景有覆盖；
- 核心接口测试覆盖率达到 100%；
- 关键业务方法覆盖率达到或超过 90%；
- 需求变更后有新增测试和回归测试；
- 留存测试类、测试日志、测试报告和覆盖率材料。

### 12.4 架构和代码质量验收

- Controller、Service、Mapper/Dao、Entity 职责清晰；
- Controller 不包含复杂业务逻辑；
- 业务规则集中且可复用；
- 有统一异常处理和统一响应封装；
- 无明显重复代码、无无必要的复杂设计；
- 需求变更不需要大面积修改无关模块；
- 命名规范，注释能解释关键业务决策。

### 12.5 文档和过程验收

交付材料至少包括：

- 软件需求规格说明书；
- 项目说明文档；
- 架构设计文档；
- 数据库设计文档；
- 接口文档；
- TDD 测试报告；
- 测试日志和覆盖率报告；
- 需求变更记录和回归测试记录；
- 团队分工和开发日志；
- 交叉验收报告；
- AI 辅助使用记录。

## 13. 团队协作与 AI 使用约束

### 13.1 团队角色

| 角色                   | 职责                                         |
| ---------------------- | -------------------------------------------- |
| 后端架构与 TDD 负责人  | 架构搭建、分层规范、统一封装和接口测试       |
| 后端业务与数据库负责人 | 数据库设计、SQL、业务实现和接口联调          |
| 前端与验收文档负责人   | 页面、交互、前后端联调和交付材料             |
| 测试与迭代适配专员     | 测试补充、回归测试、变更分析、重构和缺陷跟踪 |

角色可以由 3—4 名成员协作承担，但每项工作必须有明确责任人和 Git 贡献记录。

### 13.2 AI 允许使用的场景

- Spring Boot、DTO、Entity、Mapper 和 Vue 页面样板；
- Axios 封装、统一返回体和全局异常处理样板；
- 编译错误、依赖问题、SQL 和前端语法问题定位；
- REST 接口和 TDD 场景的方案启发；
- 接口文档、测试报告和项目报告初稿。

### 13.3 AI 使用限制

- 不得直接复制完整 Controller 或 Service 业务逻辑提交；
- 不得直接使用 AI 一次性生成的完整 TDD 测试套件；
- 接口划分、分层方案和需求变更策略必须由小组讨论决定；
- Bug 原因、测试结果和验收结论必须由小组自行判断；
- 所有 AI 产出必须经过成员理解、修改和验证；
- 小组需要记录 AI 参与的样板代码、问题定位、方案参考和文档辅助内容。
