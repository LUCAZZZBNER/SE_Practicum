## 1. 文档说明

### 1.1 编写目的

本文档用于明确轻量级外卖服务平台的业务目标、系统边界、参与者、功能需求、业务规则、非功能需求、数据约束、接口约束和验收标准，为以下工作提供统一依据：

1. 小组进行需求分析和架构设计；
2. 按照 TDD 流程设计测试用例和实现业务代码；
3. 前后端分离开发及接口联调；
4. 需求变更后的影响分析、回归测试和代码重构；
5. 组间交叉验收和项目答辩。

本文档以“业务目标 → 用例 → 业务规则 → 接口/数据 → 测试 → 验收”为主要追踪链路，后续需求变更必须同步更新受影响的内容。

### 1.2 项目背景

本项目是 26271 学期软件工程综合实践项目，项目周期为 2026-08-31 至 2026-09-20，共 3 周。系统参考饿了么等外卖平台的核心业务流程，为普通用户提供店铺和商品浏览、购物车管理、订单创建及订单查询能力，为商家提供店铺、商品分类、商品和库存管理能力。

项目不以堆叠复杂功能为目标，而以以下软件工程能力为重点：

- 测试驱动开发（TDD）的红—绿—重构流程；
- 前后端分离及清晰的接口契约；
- Controller、Service、Mapper/Dao、Entity 分层；
- 需求变化下的低耦合和可扩展架构；
- Git 过程证据和小组协作；
- 组间客观、可重复的交叉验收。

### 1.3 项目目标

#### 1.3.1 业务目标

1. 普通用户能够注册、登录并维护个人信息；
2. 普通用户能够浏览店铺、查看商品并完成购物车操作；
3. 普通用户能够根据购物车创建订单并查询订单状态；
4. 商家能够注册并管理自己的店铺；
5. 商家能够维护商品分类、商品信息、上下架状态和库存；
6. 系统能够对身份、权限、店铺状态、商品状态和库存进行校验。

#### 1.3.2 工程目标

1. 所有核心接口和核心业务方法遵循测试优先开发；
2. 核心业务接口测试覆盖率达到 100%，关键业务方法覆盖率不低于 90%；
3. 后端采用标准四层架构，避免 Controller 与数据库或复杂业务规则直接耦合；
4. 接口统一使用 `/api/v1` 版本前缀和结构化响应体；
5. 第二阶段新增需求可以通过扩展现有模块完成，不进行大面积重构；
6. 留存测试类、测试日志、覆盖率报告、Git 提交记录和需求变更记录。

## 2. 系统愿景与范围

### 2.1 系统愿景

为普通用户提供便捷的店铺浏览、商品选择、购物车管理和订单查询服务；为商家提供店铺和商品管理能力，形成一个轻量级、可测试、可扩展的外卖服务平台。

### 2.2 系统边界

#### 2.2.1 系统内

- 用户注册、登录和个人信息管理；
- 商家注册和店铺状态管理；
- 店铺列表、详情和营业状态展示；
- 商品分类、商品信息、价格和库存管理；
- 购物车增删改查；
- 基础订单创建、查询、状态展示和取消；
- 身份认证、权限控制、参数校验和统一异常处理；
- 自动化测试、回归测试和覆盖率统计。

#### 2.2.2 系统外

以下能力不属于第一阶段必做范围：

- 真实支付渠道和支付回调；
- 骑手管理、配送路径规划和实时配送调度；
- 商家结算、平台抽成和财务对账；
- 复杂推荐、搜索排序算法和个性化画像；
- 即时通讯、客服和实时聊天；
- 真实短信、邮件或第三方身份认证服务。

#### 2.2.3 后续可扩展范围

架构应为以下功能预留扩展空间，但本版本不强制实现：

- 优惠券、满减和会员折扣；
- 退款和售后；
- 用户评价和商家评分；
- 配送状态和骑手信息；
- 地址簿和收货地址管理；
- 管理员和平台运营后台。

### 2.3 系统整体流程

```text
普通用户注册/登录
        ↓
浏览店铺列表与店铺详情
        ↓
查看商品分类、商品详情和库存
        ↓
加入购物车并调整数量
        ↓
校验店铺状态、商品状态和库存
        ↓
创建订单
        ↓
查询订单详情和订单状态
```

商家侧流程：

```text
商家注册/登录
        ↓
创建或进入自己的店铺
        ↓
设置营业、关店或临时闭店状态
        ↓
维护商品分类和商品
        ↓
维护价格、库存和上下架状态
        ↓
查看店铺订单
```

## 3. 参与者分析

### 3.1 参与者定义

| 参与者     | 类型         | 主要目标                             | 触发的主要用例                     |
| ---------- | ------------ | ------------------------------------ | ---------------------------------- |
| 普通用户   | 主要参与者   | 浏览商品、管理购物车、创建并查询订单 | 注册、登录、浏览店铺、购物车、订单 |
| 商家       | 主要参与者   | 管理店铺、分类、商品和库存           | 注册商家、管理店铺、管理商品       |
| 系统       | 系统参与者   | 执行身份、状态、库存和业务规则校验   | 所有受规则约束的用例               |
| 前端客户端 | 外部交互系统 | 展示页面并调用后端接口               | 所有前后端交互用例                 |
| 数据库     | 外部支持系统 | 保存和查询业务数据                   | 用户、店铺、商品、购物车、订单     |
| 测试工具   | 外部支持工具 | 执行自动化测试、接口测试和回归测试   | TDD 测试和交叉验收                 |

### 3.2 参与者边界

- 普通用户只能操作本人拥有的个人信息、购物车和订单；
- 商家只能操作自己注册或拥有的店铺、商品分类、商品和相关订单；
- 系统负责最终业务规则校验，前端校验不能替代后端校验；
- 数据库不直接向客户端暴露；
- 前端客户端不直接访问数据库，只能通过后端接口获取数据；
- 测试工具用于验证系统，不参与正式业务数据的权限绕过。

### 4.3 用例关系说明

#### 4.3.1 创建订单包含的业务步骤

`UC-ORDER-001 创建订单` 必须包含以下步骤：

```text
验证登录状态
    ↓
读取购物车
    ↓
验证店铺状态
    ↓
验证商品状态
    ↓
验证库存
    ↓
计算金额
    ↓
创建订单与明细
    ↓
扣减库存
    ↓
清理购物车
```

#### 4.3.2 加入购物车与商品浏览的关系

用户只有在能够识别一个有效商品，并且该商品处于可购买状态时，才能执行加入购物车。商品详情或商品列表是加入购物车的前置业务信息来源，但不能将前端页面的显示状态作为最终授权依据。

#### 4.3.3 取消订单与订单状态的关系

取消订单是对订单状态的业务变更，不等同于删除订单资源，因此使用：

```text
POST /api/v1/orders/{orderId}/cancel
```

系统必须根据当前订单状态判断是否允许取消。

## 5. 功能需求

### 5.1 需求描述约定

每项功能需求至少包含：

- 需求编号和名称；
- 需求目标；
- 参与者；
- 前置条件；
- 后置条件；
- 基本事件流；
- 备选和异常事件流；
- 业务规则；
- 接口和测试追踪；
- 可验证的验收条件。

### 5.2 用户模块

#### FR-USER-001 注册账号

系统应允许未注册用户使用账号和密码创建普通用户账号。

**参与者**：普通用户。

**前置条件**：用户未登录或当前没有可用账号。

**基本事件流**：

1. 用户输入账号、密码和确认密码；
2. 系统校验必填项和格式；
3. 系统查询账号是否已经存在；
4. 系统以安全方式保存用户信息；
5. 系统返回注册成功结果。

**备选/异常流**：

- 账号为空：返回参数错误；
- 密码为空：返回参数错误；
- 两次密码不一致：返回密码不一致；
- 账号已存在：返回资源冲突；
- 密码不符合长度或复杂度要求：返回参数错误；
- 数据库保存失败：不返回成功，不产生不完整用户记录。

**后置条件**：成功时生成一个状态正常的用户账号；失败时数据库不新增无效账号。

**关联规则**：`BR-USER-001`、`BR-USER-002`。

**关联接口**：`POST /api/v1/users`。

**验收条件**：合法账号可以注册；重复账号不能注册；失败场景有明确错误提示；密码不以明文形式返回或展示。

#### FR-USER-002 登录系统

系统应允许状态正常的用户或商家使用正确凭据登录。

**参与者**：普通用户、商家。

**前置条件**：账号已经注册。

**基本事件流**：

1. 用户输入账号和密码；
2. 系统查询账号；
3. 系统校验密码；
4. 系统校验账号状态；
5. 系统生成登录凭证或会话标识；
6. 系统返回用户基本身份信息。

**备选/异常流**：

- 账号不存在：登录失败；
- 密码错误：登录失败；
- 账号被禁用：拒绝登录；
- 账号或密码为空：返回参数错误；
- 多次失败登录：本版本至少记录失败，不强制实现验证码或锁定策略。

**后置条件**：成功时客户端可以携带凭证访问受保护资源；失败时不得创建有效登录会话。

**关联接口**：`POST /api/v1/users/login`。

**验收条件**：正确凭据登录成功；错误凭据和禁用账号登录失败；未认证请求不能访问受保护资源。

#### FR-USER-003 查询个人信息

登录用户可以查询自己的账号、联系方式和账号状态等非敏感信息。

**接口**：`GET /api/v1/users/me`。

**规则**：只能返回当前登录用户信息，不返回密码；未登录时返回未认证错误。

#### FR-USER-004 修改个人信息

登录用户可以修改允许变更的个人资料。

**接口**：`PATCH /api/v1/users/me`。

**规则**：只能修改本人资料；账号唯一标识默认不允许随意修改；提交空值或非法格式时更新失败；更新失败时不得保存部分无效数据。

### 5.3 商家和店铺模块

#### FR-MERCHANT-001 注册商家

系统应允许用户或未注册经营者创建商家账号，具体注册身份规则由项目实现时确定并保持一致。

**接口建议**：`POST /api/v1/merchants`。

**异常场景**：重复账号、必填字段缺失、联系方式格式错误、密码不符合要求。

**验收条件**：注册成功后商家可登录；商家资料与普通用户资料权限隔离。

#### FR-SHOP-001 创建店铺

登录商家可以创建属于自己的店铺。

**前置条件**：商家已登录并具有创建店铺权限。

**基本事件流**：

1. 商家提交店铺名称、简介等信息；
2. 系统校验商家身份和字段格式；
3. 系统检查店铺名称和归属关系；
4. 系统创建店铺；
5. 系统返回店铺信息。

**异常流**：商家未登录、无权创建、名称为空、重复创建不符合规则、数据库保存失败。

**初始状态**：新建店铺默认为关店或待营业状态，具体初始值必须在实现和测试中统一。

**接口**：`POST /api/v1/shops`。

#### FR-SHOP-002 修改店铺状态

商家可以将自己店铺的状态设置为营业、关店或临时闭店。

**接口建议**：`PATCH /api/v1/shops/{shopId}`。

**规则**：

- 商家不能修改其他商家的店铺；
- 状态必须是系统允许的枚举值；
- 关店或临时闭店后不能创建新的订单；
- 状态变更不能删除店铺或历史订单。

#### FR-SHOP-003 浏览店铺列表

普通用户可以分页查询店铺列表，并查看店铺名称、简介和营业状态。

**接口**：`GET /api/v1/shops`。

**查询参数**：`page`、`pageSize`、`keyword`、`status`、`sortBy`、`sortOrder`。

**边界规则**：页码从 1 开始；页大小必须为正数且不超过系统上限；无匹配结果返回空列表而非错误。

#### FR-SHOP-004 查看店铺详情

普通用户可以查看指定店铺的详细信息和当前状态。

**接口**：`GET /api/v1/shops/{shopId}`。

**异常流**：店铺不存在返回资源不存在；店铺已逻辑删除时不作为可用店铺返回。

### 5.4 商品模块

#### FR-PRODUCT-001 管理商品分类

商家可以在自己的店铺中新增、修改、查询和逻辑删除商品分类。

**接口建议**：

```text
POST   /api/v1/shops/{shopId}/categories
GET    /api/v1/shops/{shopId}/categories
PATCH  /api/v1/categories/{categoryId}
DELETE /api/v1/categories/{categoryId}
```

**规则**：分类必须归属于当前商家店铺；分类名称不能为空；存在有效商品的分类不能被无条件物理删除。

#### FR-PRODUCT-002 新增商品

商家可以向自己的店铺和商品分类中新增商品。

**基本字段**：商品名称、分类、价格、库存、描述、状态。

**基本事件流**：

1. 商家提交商品信息；
2. 系统校验商家和店铺归属；
3. 系统校验商品分类；
4. 系统校验价格和库存；
5. 系统保存商品；
6. 系统返回商品信息。

**规则**：价格必须大于 0；库存必须大于或等于 0；新商品默认下架或按项目统一约定的初始状态保存；下架商品不能被普通用户购买。

**接口**：`POST /api/v1/products`。

#### FR-PRODUCT-003 修改商品

商家可以局部修改自己商品的名称、描述、分类、价格等允许修改的字段。

**接口**：`PATCH /api/v1/products/{productId}`。

**规则**：修改商品时必须重新校验所有被修改字段；不能修改其他商家的商品；已经产生历史订单的商品修改价格不得改变历史订单明细中的成交单价。

#### FR-PRODUCT-004 管理商品状态和库存

商家可以上架、下架商品并调整库存。

**接口建议**：

```text
PATCH /api/v1/products/{productId}
```

**规则**：库存不能小于 0；库存为 0 时商品不得被当作有货商品；下架商品可以保留历史数据，但不能加入购物车或创建新订单。

#### FR-PRODUCT-005 浏览商品

普通用户可以查看指定店铺的商品分类、商品列表和商品详情。

**接口建议**：

```text
GET /api/v1/shops/{shopId}/products
GET /api/v1/products/{productId}
```

**查询参数**：`categoryId`、`keyword`、`page`、`pageSize`、`sortBy`、`sortOrder`。

**规则**：普通用户默认只能看到上架商品；商品列表必须展示价格和库存状态；商品详情不存在或不属于指定店铺时返回错误。

### 5.5 购物车模块

#### FR-CART-001 加入购物车

登录用户可以将可购买商品加入购物车。

**前置条件**：用户已登录；商品存在、属于有效店铺、处于上架状态且库存充足。

**基本事件流**：

1. 用户选择商品和数量；
2. 系统验证用户身份；
3. 系统读取商品和店铺状态；
4. 系统校验数量和库存；
5. 若购物车已有该商品则增加数量，否则创建购物车项；
6. 系统返回购物车项。

**异常流**：未登录、商品不存在、商品下架、店铺不可营业、数量非正整数、数量超过库存。

**接口**：`POST /api/v1/cart-items`。

#### FR-CART-002 查询购物车

登录用户可以查询自己的购物车及商品小计。

**接口**：`GET /api/v1/cart-items`。

**规则**：只返回当前用户购物车；展示商品最新状态，但不擅自修改订单历史；购物车为空返回空列表。

#### FR-CART-003 修改购物车数量

用户可以调整自己购物车项的数量。

**接口**：`PATCH /api/v1/cart-items/{itemId}`。

**规则**：数量必须为正整数且不能超过当前库存；购物车项不存在或不属于当前用户时不能修改；若商品已下架或店铺不可营业，系统应提示用户而不是默默提交。

#### FR-CART-004 删除购物车商品

用户可以删除自己的购物车项。

**接口**：`DELETE /api/v1/cart-items/{itemId}`。

**规则**：删除购物车项不影响商品库存和历史订单；重复删除已不存在项目时返回明确结果，不得删除其他用户项目。

### 5.6 订单模块

#### FR-ORDER-001 创建订单

用户可以根据有效购物车内容创建订单。该用例是本项目的核心业务用例，必须重点进行单元测试、接口测试和事务测试。

**参与者**：普通用户；系统、数据库为支持参与者。

**触发条件**：用户在购物车页面提交订单。

**前置条件**：

- 用户已登录；
- 购物车不为空；
- 购物车商品满足店铺归属规则；
- 店铺处于营业状态；
- 商品处于上架状态；
- 每个商品库存满足购买数量。

**成功后置条件**：

- 创建订单主记录；
- 创建订单明细；
- 保存下单时的商品名称、成交单价和数量；
- 计算并保存订单总金额；
- 扣减库存；
- 清理已提交的购物车项；
- 返回订单编号和订单摘要。

**失败后置条件**：

- 不生成不完整订单；
- 不错误扣减库存；
- 不错误删除购物车项；
- 返回可理解的业务错误；
- 数据库异常时事务回滚。

**基本事件流**：

1. 用户提交购物车商品；
2. 系统验证登录状态；
3. 系统读取购物车、商品和店铺信息；
4. 系统检查店铺营业状态；
5. 系统检查商品是否上架；
6. 系统检查商品库存；
7. 系统按照当前有效价格计算金额；
8. 系统创建订单和订单明细；
9. 系统扣减库存；
10. 系统删除已购买的购物车记录；
11. 系统提交事务并返回结果。

**备选事件流**：

- 商品价格发生变化：提示用户确认最新价格，本版本不得无提示地使用客户端旧价格；
- 商品部分缺货：默认整笔订单创建失败并指出缺货商品；
- 购物车包含多个店铺商品：默认拒绝提交并提示按店铺分别下单；若后续改为自动拆单，必须新增需求和测试；
- 店铺临时闭店：创建失败并提示店铺暂不可下单；
- 重复提交：使用请求幂等策略或业务校验避免生成重复订单。

**异常事件流**：

- 用户未登录：返回 401；
- 购物车为空：返回 400；
- 商品或店铺不存在：返回 404；
- 库存不足：返回 409；
- 数据库写入失败：事务回滚并返回服务器错误；
- 网络异常：客户端不得将未确认的请求显示为已成功。

**关联规则**：`BR-ORDER-001` 至 `BR-ORDER-008`。

**接口**：`POST /api/v1/orders`。

**验收条件**：合法购物车可以成功下单；所有非法状态被拒绝；失败后库存和购物车保持正确；订单明细保留下单时成交信息；相关测试全部通过。

#### FR-ORDER-002 查询订单列表

登录用户可以分页查询自己的订单列表。

**接口**：`GET /api/v1/orders`。

**查询参数**：`status`、`page`、`pageSize`、`sortBy`、`sortOrder`。

**规则**：只能返回当前用户订单；默认按创建时间倒序；无订单返回空列表；分页参数必须校验。

#### FR-ORDER-003 查看订单详情

登录用户可以查看自己的订单主信息、订单明细、总金额、店铺和订单状态。

**接口**：`GET /api/v1/orders/{orderId}`。

**规则**：订单不存在返回 404；订单属于其他用户时不得泄漏详情，可统一返回无权访问或资源不存在；历史订单使用下单时的商品名称和成交单价。

#### FR-ORDER-004 取消订单

用户可以在允许取消的状态下取消自己的订单。

**接口**：`POST /api/v1/orders/{orderId}/cancel`。

**基本事件流**：

1. 用户提交取消请求；
2. 系统验证用户身份和订单归属；
3. 系统检查订单当前状态；
4. 系统将订单状态修改为已取消；
5. 若业务规则要求，系统恢复相应库存；
6. 系统返回取消结果。

**异常流**：订单不存在、订单属于其他用户、订单已完成、订单已取消、订单处于不可取消状态、状态并发冲突。

**规则**：取消操作是状态变化，不删除订单主记录和订单明细；允许取消的状态必须由系统统一定义并写入测试。

## 6. 业务规则与状态模型

### 6.1 用户规则

| 编号        | 业务规则                                         |
| ----------- | ------------------------------------------------ |
| BR-USER-001 | 用户账号必须唯一，不能为空。                     |
| BR-USER-002 | 密码必须安全存储，任何响应不得返回密码明文。     |
| BR-USER-003 | 账号禁用后不能登录或执行需要身份认证的业务操作。 |
| BR-USER-004 | 用户只能查询和修改自己的个人信息。               |

### 6.2 商家和店铺规则

| 编号        | 业务规则                                         |
| ----------- | ------------------------------------------------ |
| BR-SHOP-001 | 店铺必须归属于一个有效商家。                     |
| BR-SHOP-002 | 商家只能管理自己拥有的店铺。                     |

| BR-SHOP-004 | 关店或临时闭店的店铺不能创建新订单。             |
| BR-SHOP-005 | 店铺状态变更不删除历史商品和订单。               |

### 6.3 商品规则

| 编号           | 业务规则                                               |
| -------------- | ------------------------------------------------------ |
| BR-PRODUCT-001 | 商品必须归属于有效店铺和有效分类。                     |
| BR-PRODUCT-002 | 商品价格必须大于 0。                                   |
| BR-PRODUCT-003 | 商品库存必须大于或等于 0。                             |
| BR-PRODUCT-004 | 下架商品不能加入购物车或创建新订单。                   |
| BR-PRODUCT-005 | 商家只能管理自己店铺中的商品。                         |
| BR-PRODUCT-006 | 历史订单保存成交快照，商品后续改价不影响历史订单金额。 |

| 编号        | 业务规则                                       |
| ----------- | ---------------------------------------------- |

### 6.5 订单规则

| 编号         | 业务规则                                                   |
| ------------ | ---------------------------------------------------------- |
| BR-ORDER-001 | 只有登录用户可以创建订单。                                 |
| BR-ORDER-002 | 创建订单时必须重新检查店铺营业状态。                       |
| BR-ORDER-003 | 创建订单时必须重新检查商品上架状态。                       |
| BR-ORDER-004 | 任一商品库存不足时，默认整笔订单创建失败。                 |
| BR-ORDER-005 | 订单金额由服务端根据有效商品价格计算，不能信任客户端金额。 |
| BR-ORDER-006 | 订单、订单明细、库存和购物车清理必须保持事务一致性。       |
| BR-ORDER-007 | 订单明细必须保存下单时的商品名称、成交单价和数量。         |
| BR-ORDER-008 | 取消订单只能通过状态迁移完成，不能物理删除历史订单。       |
| BR-ORDER-009 | 重复提交同一业务请求不能产生未预期的重复订单。             |

### 6.6 状态模型

#### 用户状态

```text
正常 ─────────→ 禁用
禁用 ─────────→ 正常（仅允许有权限的管理操作）
```

#### 店铺状态

```text
关店 ─────────→ 营业
营业 ─────────→ 关店
营业 ─────────→ 临时闭店
临时闭店 ─────→ 营业
临时闭店 ─────→ 关店
```

#### 商品状态

```text
下架 ─────────→ 上架
上架 ─────────→ 下架
```

#### 订单状态

第一阶段至少支持以下状态：

```text
待支付 → 已支付 → 制作中 → 配送中 → 已完成
待支付 ─────────────────────→ 已取消
已支付 ─────────────────────→ 已取消（是否允许由业务规则决定）
```

真实支付未纳入本版本范围时，可以将“待支付”作为基础订单初始状态，并明确模拟支付或跳过支付的测试约定。

## 7. 数据需求

### 7.1 数据对象总览

```text
用户 1 ─── N 订单
用户 1 ─── N 购物车项
商家 1 ─── N 店铺
店铺 1 ─── N 商品分类
店铺 1 ─── N 商品
店铺 1 ─── N 订单
商品分类 1 ─── N 商品
订单 1 ─── N 订单明细
商品 1 ─── N 购物车项
商品 1 ─── N 订单明细
```

### 7.2 用户对象

**含义**：平台登录和权限校验的用户主体。

**核心属性**：用户 ID、账号、密码摘要、昵称、联系方式、状态、创建时间、更新时间。

**约束**：用户 ID 唯一；账号非空且唯一；密码不得明文保存；状态只能取系统定义值。

**生命周期**：注册、正常使用、禁用或逻辑删除。

**访问权限**：用户可读取和修改自己的非敏感信息；商家管理自己的商家资料；其他用户不得读取。

**扩展方向**：头像、收货地址、用户角色、最后登录时间。

### 7.3 商家对象

**含义**：店铺经营主体。

**核心属性**：商家 ID、关联账号、商家名称、联系方式、状态、创建时间。

**约束**：商家必须关联有效账号；商家状态影响店铺管理权限。

**访问权限**：商家只能读取和修改自己的资料；普通用户只能查看必要展示信息。

### 7.4 店铺对象

**含义**：商家提供商品和接收订单的经营主体。

**核心属性**：店铺 ID、商家 ID、店铺名称、简介、状态、创建时间、更新时间。

**约束**：必须关联一个商家；状态必须是营业、关店或临时闭店；逻辑删除后不能作为有效店铺使用。

**扩展方向**：营业时间、店铺图片、起送价、配送费、公告。

### 7.5 商品分类对象

**含义**：店铺内组织商品的分类。

**核心属性**：分类 ID、店铺 ID、分类名称、排序号、状态、创建时间。

**约束**：同一店铺内分类名称不得违反唯一性规则；存在商品引用时应优先逻辑删除或阻止删除。

### 7.6 商品对象

**含义**：用户可以浏览和购买的商品。

**核心属性**：商品 ID、店铺 ID、分类 ID、名称、描述、价格、库存、上下架状态、创建时间、更新时间。

**约束**：价格大于 0；库存不小于 0；商品必须归属于有效店铺；历史订单不依赖商品当前名称和价格。

### 7.7 购物车项对象

**含义**：用户选择但尚未形成订单的商品记录。

**核心属性**：购物车项 ID、用户 ID、商品 ID、数量、创建时间、更新时间。

**约束**：用户和商品必须有效；数量为正整数；同一用户同一商品原则上只保留一个购物车项。

### 7.8 订单对象

**含义**：用户提交购买请求后形成的业务记录。

**核心属性**：订单 ID、订单编号、用户 ID、店铺 ID、总金额、订单状态、创建时间、更新时间、取消时间。

**约束**：订单编号唯一；总金额由服务端计算；订单状态必须遵守状态迁移规则；历史订单不得因商品当前数据变化而改变。

### 7.9 订单明细对象

**含义**：订单中的商品快照和数量记录。

**核心属性**：明细 ID、订单 ID、商品 ID、商品名称快照、成交单价、购买数量、小计。

**约束**：成交单价和商品名称在创建订单时写入；小计由服务端计算；订单明细不能脱离订单单独存在。

### 7.10 数据一致性要求

- 外键关联数据必须存在或经过明确的逻辑删除处理；
- 创建订单的关键写操作必须在一个事务中完成；
- 库存扣减不能导致库存为负数；
- 订单创建失败时，订单、订单明细、库存和购物车项必须恢复到操作前状态；
- 订单历史金额不随商品后续改价变化；
- 删除操作默认采用逻辑删除，避免破坏历史业务数据。

## 8. 外部接口与系统接口需求

### 8.1 接口总约定

1. 所有业务接口使用 `/api/v1` 版本前缀；
2. URI 以资源名词为中心，避免 `/createOrder`、`/updateGoods` 等动词型路径；
3. `GET` 只执行查询，不修改数据；
4. `POST` 用于创建资源或执行明确的业务动作；
5. `PUT` 表示全量更新，`PATCH` 表示局部更新；
6. `DELETE` 表示删除或逻辑删除；
7. 分页、过滤和排序使用 Query 参数；
8. 使用标准 HTTP 状态码；
9. 后端不得信任客户端传入的金额、权限、商品状态和库存结果；
10. 详细字段定义以后续接口文档为准，但不得违反本需求基线。

### 8.2 统一响应结构

```json
{
  "code": 0,
  "msg": "操作成功",
  "data": {}
}
```

成功响应中的 `data` 根据接口返回对象确定；列表接口应包含列表和分页信息。失败响应必须包含稳定的错误码和可理解的提示信息，不能将异常堆栈直接返回给客户端。

### 8.3 状态码约定

| 状态码                    | 使用场景                       |
| ------------------------- | ------------------------------ |
| 200 OK                    | 查询或更新成功                 |
| 201 Created               | 创建资源成功                   |
| 204 No Content            | 删除成功且不返回正文时使用     |
| 400 Bad Request           | 参数格式、缺失或业务请求不合法 |
| 401 Unauthorized          | 未认证或登录凭证无效           |
| 403 Forbidden             | 已认证但没有资源操作权限       |
| 404 Not Found             | 资源不存在                     |
| 409 Conflict              | 资源冲突、库存冲突或状态冲突   |
| 500 Internal Server Error | 未预期的服务端错误             |

### 8.4 核心接口清单

| 方法   | URI                                 | 用例               | 说明           |
| ------ | ----------------------------------- | ------------------ | -------------- |
| POST   | `/api/v1/users`                   | UC-USER-001        | 注册普通用户   |
| POST   | `/api/v1/users/login`             | UC-USER-002        | 用户或商家登录 |
| GET    | `/api/v1/users/me`                | UC-USER-003        | 查询当前用户   |
| PATCH  | `/api/v1/users/me`                | UC-USER-004        | 修改当前用户   |
| POST   | `/api/v1/merchants`               | UC-MERCHANT-001    | 注册商家       |
| POST   | `/api/v1/shops`                   | UC-SHOP-001        | 创建店铺       |
| GET    | `/api/v1/shops`                   | UC-SHOP-003        | 店铺列表       |
| GET    | `/api/v1/shops/{shopId}`          | UC-SHOP-004        | 店铺详情       |
| PATCH  | `/api/v1/shops/{shopId}`          | UC-SHOP-002        | 修改店铺状态   |
| GET    | `/api/v1/shops/{shopId}/products` | UC-PRODUCT-005     | 店铺商品列表   |
| GET    | `/api/v1/products/{productId}`    | UC-PRODUCT-005     | 商品详情       |
| POST   | `/api/v1/products`                | UC-PRODUCT-002     | 新增商品       |

| GET    | `/api/v1/orders/{orderId}`        | UC-ORDER-003       | 订单详情       |
| POST   | `/api/v1/orders/{orderId}/cancel` | UC-ORDER-004       | 取消订单       |

### 8.5 分页、过滤和排序

列表接口统一支持需要的 Query 参数：

```text
page=1&pageSize=10&keyword=汉堡&status=OPEN&sortBy=createdAt&sortOrder=desc
```

约束：

- `page` 从 1 开始；
- `pageSize` 大于 0 且不超过统一上限；
- 不认识的排序字段必须拒绝或使用安全的默认字段，不能直接拼接 SQL；
- 过滤条件由具体资源定义；
- 空结果返回成功状态和空列表。

## 9. 非功能需求

### 9.1 性能需求

| 编号         | 需求                                                           |
| ------------ | -------------------------------------------------------------- |
| NFR-PERF-001 | 普通查询接口在本地正常运行环境下平均响应时间目标不超过 2 秒。  |
| NFR-PERF-002 | 列表接口必须使用分页，默认每页 10 条，单页上限由统一配置控制。 |
| NFR-PERF-003 | 订单创建应避免重复读取和无必要的跨层调用。                     |

以上指标用于课程实践验收，不等同于生产环境容量承诺。

### 9.2 安全和权限需求

| 编号        | 需求                                                   |
| ----------- | ------------------------------------------------------ |
| NFR-SEC-001 | 密码不得明文存储、日志输出或接口返回。                 |
| NFR-SEC-002 | 购物车、订单和个人信息接口必须验证身份。               |
| NFR-SEC-003 | 服务端必须校验资源归属，不能只依赖前端隐藏按钮。       |
| NFR-SEC-004 | 用户不能访问其他用户的购物车和订单详情。               |
| NFR-SEC-005 | 商家不能管理其他商家的店铺、商品和库存。               |
| NFR-SEC-006 | 错误响应不得暴露数据库结构、密码、堆栈和内部敏感配置。 |

### 9.3 可维护性和架构需求

- 后端严格划分 Entity、Mapper/Dao、Service、Controller；
- Controller 负责请求接收、参数校验和响应转换，不写复杂业务逻辑；
- Mapper/Dao 只负责数据库操作，不承载跨资源业务规则；
- Service 负责业务规则、事务和需求变化相关的扩展点；
- 使用统一异常处理器，新增业务异常不重复编写 Controller 捕获逻辑；
- 使用统一响应对象，前端不因单个接口格式变化而大面积修改；
- 通用参数校验、状态判断和时间处理应适当封装；
- 前端采用路由分层和组件化，Axios 统一处理请求和响应；
- 命名、注释和目录结构保持一致，避免无意义的过度设计。

### 9.4 可测试性需求

- 所有核心接口必须有测试；
- 核心业务接口覆盖率 100%；
- 关键业务方法覆盖率不低于 90%；
- 测试至少覆盖正常、异常和边界场景；
- 权限、状态迁移、库存一致性和事务回滚必须有测试；
- 每个测试必须包含有效断言；
- 需求变更后必须新增测试并执行原有功能回归测试；
- 测试结果、覆盖率和日志应保存到项目交付材料中。

### 9.5 可用性需求

- 表单提交前进行必要的必填和格式校验；
- 服务端返回的错误信息应能被前端转换为用户可理解的提示；
- 列表为空时显示空数据状态；
- 网络请求失败时显示重试或返回建议；
- 订单提交过程中应避免重复点击造成重复请求；
- 商品下架、缺货和店铺闭店状态应在页面上明确展示。

### 9.6 可扩展性需求

- 接口统一使用 `/api/v1`，破坏性变更时可增加 `/api/v2`；
- 优惠、退款等新资源通过新增资源路径接入，不修改无关旧接口；
- 订单规则、价格计算和库存处理集中在 Service 层；
- 状态值使用统一枚举或常量管理，避免散落字符串；
- 统一异常和响应封装，降低新增模块的接入成本；
- 需求变更优先通过新增用例、规则和服务能力实现，避免大面积重构。

## 10. TDD 开发与测试需求

### 10.1 强制开发流程

项目必须遵循以下顺序：

```text
梳理业务目标和用例
        ↓
明确接口行为和验收条件
        ↓
编写测试用例
        ↓
运行测试并确认失败（Red）
        ↓
编写最少业务代码
        ↓
运行测试并确认通过（Green）
        ↓
重构并保持测试通过（Refactor）
        ↓
提交代码并保留过程证据
```

禁止先完成业务代码再集中补测试，禁止测试没有断言，禁止跳过测试直接提交功能。

### 10.2 测试类型

| 类型                | 目标                           | 主要工具            |
| ------------------- | ------------------------------ | ------------------- |
| Service 单元测试    | 验证核心业务规则和分支         | JUnit 5、Mockito    |
| Controller/API 测试 | 验证 HTTP 方法、状态码和响应体 | MockMvc             |
| Mapper 测试         | 验证数据库查询和持久化行为     | JUnit 5、测试数据库 |
| 前端组件测试        | 验证页面交互和展示状态         | Vitest（可选）      |
| 接口联调测试        | 验证前后端契约                 | Postman/ApiFox      |
| 回归测试            | 验证变更没有破坏旧功能         | 自动化测试集合      |

### 10.3 测试场景要求

核心用例必须考虑：

- 合法输入和成功结果；
- 缺失参数、格式错误和非法值；
- 空数据、零库存、最大数量和分页边界；
- 未登录、凭证无效和权限不足；
- 资源不存在、资源归属错误和重复资源；
- 店铺状态、商品状态和订单状态冲突；
- 并发或重复提交导致的库存和订单一致性问题；
- 数据库失败后的事务回滚；
- 需求变更后的新规则和旧功能回归。

| UC-USER-002    | FR-USER-002    | BR-USER-003    | TC-USER-003 禁用账号登录失败 |

每个功能迭代至少保留能够体现以下顺序的提交或等价过程记录：

1. 需求或用例分析；
2. 测试用例提交；
3. 测试失败记录；
4. 业务实现提交；
5. 测试通过记录；
6. 重构提交；
7. 回归测试结果。

提交信息应能够说明功能或测试范围，不允许在临近提交日期时一次性集中上传全部代码。

### 11.2 变更处理流程

1. 记录原始需求、新需求和变更原因；
2. 识别受影响的参与者和用例；
3. 识别受影响的业务规则、接口、数据对象和页面；
4. 先新增或修改测试用例；

6. 在现有分层架构中实现变更；

8. 检查是否出现重复代码、跨层耦合或大面积重构；
9. 更新本说明书、接口文档、测试报告和变更记录；
10. 由小组完成变更验收并保留解释材料。

## 12. 交付与验收标准

### 12.1 功能验收

- 用户、商家、店铺、商品、购物车和基础订单功能均可按照用例完成；
- 正常流程可以得到正确结果；
- 异常流程返回明确错误；
- 边界场景不会造成非法数据；
- 用户和商家权限边界有效；
- 订单失败时库存和购物车保持一致。

### 12.2 REST 接口验收

- 接口统一使用 `/api/v1`；
- URI 以资源名词为中心；
- HTTP 方法语义基本正确；
- 取消订单等业务动作使用允许的动作型子路径；
- 状态码和统一响应体符合本说明书；
- 分页、过滤、排序使用 Query 参数；
- 接口参数和错误场景有文档说明。

### 12.3 TDD 验收

- 测试用例先于对应业务实现提交；
- 测试包含有效断言；
- 正常、异常、边界和权限场景有覆盖；
- 核心接口测试覆盖率达到 100%；
- 关键业务方法覆盖率达到或超过 90%；
- 需求变更后有新增测试和回归测试；
- 留存测试类、测试日志、测试报告和覆盖率材料。

### 12.4 架构和代码质量验收

- Controller、Service、Mapper/Dao、Entity 职责清晰；
- Controller 不包含复杂业务逻辑；
- 业务规则集中且可复用；
- 有统一异常处理和统一响应封装；
- 无明显重复代码、无无必要的复杂设计；
- 需求变更不需要大面积修改无关模块；
- 命名规范，注释能解释关键业务决策。

### 12.5 文档和过程验收

交付材料至少包括：

- 软件需求规格说明书；
- 项目说明文档；
- 架构设计文档；
- 数据库设计文档；
- 接口文档；
- TDD 测试报告；
- 测试日志和覆盖率报告；
- 需求变更记录和回归测试记录；
- 团队分工和开发日志；
- 交叉验收报告；
- AI 辅助使用记录。

### 12.6 交叉验收检查清单

| 检查项     | 通过条件                               |

## 13. 团队协作与 AI 使用约束

### 13.1 团队角色

| 角色                   | 职责                                         |
| ---------------------- | -------------------------------------------- |
| 后端架构与 TDD 负责人  | 架构搭建、分层规范、统一封装和接口测试       |
| 后端业务与数据库负责人 | 数据库设计、SQL、业务实现和接口联调          |

| 测试与迭代适配专员     | 测试补充、回归测试、变更分析、重构和缺陷跟踪 |

角色可以由 3—4 名成员协作承担，但每项工作必须有明确责任人和 Git 贡献记录。

### 13.2 AI 允许使用的场景

- Spring Boot、DTO、Entity、Mapper 和 Vue 页面样板；
- Axios 封装、统一返回体和全局异常处理样板；
- 编译错误、依赖问题、SQL 和前端语法问题定位；
- REST 接口和 TDD 场景的方案启发；
- 接口文档、测试报告和项目报告初稿。

### 13.3 AI 使用限制

- 不得直接复制完整 Controller 或 Service 业务逻辑提交；
- 不得直接使用 AI 一次性生成的完整 TDD 测试套件；
- 接口划分、分层方案和需求变更策略必须由小组讨论决定；
- Bug 原因、测试结果和验收结论必须由小组自行判断；
- 所有 AI 产出必须经过成员理解、修改和验证；
- 小组需要记录 AI 参与的样板代码、问题定位、方案参考和文档辅助内容。
