# 轻量级外卖服务平台 TDD 测试计划

## 1. 测试目标

测试计划在编码前锁定接口行为和核心业务规则，保证实现从需求出发而不是从代码反推。测试必须能够证明：

1. 正常流程可完成，返回结构、状态码和数据准确。
2. 参数错误、资源不存在、角色错误、资源越权和业务冲突被稳定识别。
3. 库存、价格版本、幂等、订单状态和事务边界在边界条件及并发竞争下保持一致。
4. 第二阶段需求变化不会破坏第一阶段已实现行为。

## 2. 测试层次与工具

| 层次 | 目标 | 工具与范围 |
| --- | --- | --- |
| 服务契约测试 | 验证每个 Service 的业务规则、跨模块调用和异常 | JUnit 5、Mockito；覆盖 user、merchant、restaurant、item、shopping、order |
| 控制器测试 | 验证路径、HTTP 方法、校验、状态码、返回外壳和权限 | JUnit 5、MockMvc |
| DAO 集成测试 | 验证 SQL、映射、约束、分页、版本更新和迁移后结构 | JUnit 5、MySQL 测试库 |
| 前端单元与集成测试 | 验证 API 适配、路由守卫和关键页面行为 | Vitest、Vue Test Utils、jsdom |
| 全量回归 | 验证需求变化后原有接口和核心流程 | 后端 Maven 测试、前端 Vitest |

控制器测试不替代服务测试；服务测试不假设控制器已经执行过校验。每层都对自己的边界负责。

## 3. 强制红—绿—重构流程

每个接口或核心业务方法按以下顺序推进：

1. 从需求和接口设计中写出测试名称、输入、预期状态、业务码和结果。
2. 先运行新增测试，保留失败输出和测试日志，确认测试确实能识别缺失行为。
3. 编写能使测试通过的最小实现，不在控制器中堆积业务逻辑。
4. 再次运行新增测试及相关回归测试，全部通过后提交实现。
5. 在测试保护下重构，重构后再次运行完整相关测试。

测试类必须有有效断言，禁止跳过测试、空测试、只验证无异常或先写实现后补测试。每次功能提交在 Git 历史中应能看出测试先于业务代码。

## 4. 统一断言要求

### 4.1 控制器

每个接口至少断言：

- HTTP 状态码；
- `code`、`msg`、`data` 三个顶层字段；
- 成功时关键字段和值；
- 失败时业务码和必要的错误数据；
- 受保护接口的缺失令牌、错误角色和资源归属。

### 4.2 服务

每个方法至少断言：

- 成功返回对象的关键字段；
- 失败时抛出的业务错误；
- DAO 或跨模块 Service 的调用参数；
- 写操作成功和失败时不应发生的后续调用；
- 事务流程中的回滚边界（通过交互验证或集成测试验证）。

### 4.3 DAO

集成测试至少断言：

- 插入后的生成主键和字段；
- 唯一、外键、检查约束；
- 逻辑删除过滤；
- 分页总数和排序稳定性；
- 版本匹配、库存足够时的受影响行数，以及冲突时的零行更新。

## 5. 服务行为矩阵

### 5.1 用户与商家

| 场景 | 预期 |
| --- | --- |
| 注册有效账号 | 创建 `ACTIVE` 记录，密码为哈希，返回资料 |
| 账号重复 | 用户返回 1101，商家返回 1201，HTTP 409 |
| 必填字段为空或全空白 | 1001，HTTP 400 |
| 用户两次密码不一致 | 1001，HTTP 400 |
| 商家提供不一致的确认密码 | 1001，HTTP 400 |
| 正确凭据登录 | 返回令牌、类型、有效期、主体和角色 |
| 账号不存在或密码错误 | 1102，HTTP 401，不区分具体原因 |
| 用户禁用或商家暂停后登录 | 分别返回 1103 或 1202 |
| 查询或修改他人资料 | 由令牌主体决定，只能访问当前主体 |
| PATCH 空 Body | 1001，HTTP 400 |
| PATCH 显式更新为 null/空白 | 按字段规则接受或返回 1001 |

### 5.2 店铺与商品

| 场景 | 预期 |
| --- | --- |
| 商家创建店铺 | 默认 `CLOSED`，返回 201 |
| 同商家重复店名 | 1005，HTTP 409 |
| 公开店铺列表 | 只显示未删除且 `OPEN` 的店铺，支持分页、关键字、状态和排序 |
| 商家 `mine=true` | 仅显示本人店铺；无商家身份返回 1003 |
| 非所有者修改店铺/分类/商品 | 1003，HTTP 403 |
| 创建分类、商品 | 校验归属、必填字段、价格、库存和排序范围 |
| 创建或修改商品时使用其他店铺分类 | 1005，HTTP 409 |
| 按不属于路径店铺的分类筛选商品 | 1004，HTTP 404 |
| 删除仍被商品引用的分类 | 1005，分类保持可见 |
| 公开查询下架商品 | 1004；店主携带 `includeOffSale=true` 可查询 |
| 商品价格、库存、状态更新 | 版本匹配时成功且版本加一 |
| 商品版本缺失或不匹配 | 1001 或 1005，不能修改 |
| 负库存、零价格、非法状态、非法排序 | 1001 |
| 并发预占库存 | 库存充足且版本匹配只成功一次，不能出现负数 |
| 预占后恢复库存 | 恢复正确数量；无效商品返回 1004 |

### 5.3 购物车

| 场景 | 预期 |
| --- | --- |
| 加入在售且营业商品 | 新条目返回 201 |
| 重复加入同商品 | 数量合并，返回 200，不新增记录 |
| 店铺未营业、商品下架或库存不足 | 分别返回 1301、1401、1402 |
| 修改数量为 0、负数或超过库存 | 1001 或 1402，原数量不变 |
| 查看购物车 | 返回当前商品信息、小计、可用性和总额 |
| 商品后来下架、店铺关闭或库存减少 | 条目标记不可用并提供原因 |
| 删除自己的条目 | 返回删除结果 |
| 删除他人或不存在条目 | 1004 |

### 5.4 订单

| 场景 | 预期 |
| --- | --- |
| 缺少、空白或超长幂等键 | 1001 |
| 空条目、重复条目、非正编号或版本 | 1001 或 1501 |
| 选中多个店铺 | 1502，HTTP 400 |
| 购物车条目不属于当前用户 | 1501 或 1004，且不扣库存 |
| 店铺关闭、商品下架、库存不足 | 对应 1301、1401、1402，且事务回滚 |
| 商品版本变化 | 1601，HTTP 409，库存、订单和购物车保持原状 |
| 有效创建订单 | 201，订单状态 `PENDING_PAYMENT`，写快照、扣库存、清购物车 |
| 相同用户和幂等键、请求相同 | 返回原订单，不重复写入或扣库存 |
| 相同幂等键、请求不同 | 1603，HTTP 409 |
| 用户查看自己的订单 | 返回摘要或详情 |
| 用户访问他人订单 | 1004，不泄露订单数据 |
| 商家筛选自己店铺订单 | 返回分页结果；非本人店铺不可查询 |
| 取消待支付订单 | 状态改为 `CANCELLED`、记录时间、恢复库存 |
| 取消其他状态订单或重复取消 | 1602，不重复恢复库存 |

## 6. 控制器接口测试清单

为以下每个端点建立正常、验证失败、未认证和越权（适用时）用例：

GET    /api/v1/merchants/me
PATCH  /api/v1/merchants/me
POST   /api/v1/shops
GET    /api/v1/shops
GET    /api/v1/shops/{shopId}
PATCH  /api/v1/shops/{shopId}
POST   /api/v1/shops/{shopId}/categories
GET    /api/v1/shops/{shopId}/categories
PATCH  /api/v1/categories/{categoryId}
DELETE /api/v1/categories/{categoryId}
POST   /api/v1/products

## 7. 安全测试

- 公开注册、登录和公开查询不应因缺少令牌失败。
- 缺少、格式错误、空白、伪造、过期或签名错误的令牌返回 1002。
- `USER` 令牌访问商家接口、`MERCHANT` 令牌访问用户接口返回 1003。
- 合法角色访问不属于自己的店铺、分类、商品、购物车或订单返回 1003 或 1004，并且不改变数据。
- 路由守卫测试只验证用户体验层跳转；服务端授权测试必须独立存在。

## 8. 测试数据与隔离

每个测试准备最小数据集，使用唯一账号和可识别的店铺、商品编号。服务单元测试使用 mock DAO 和公开 Service；DAO 集成测试在每个测试后清理数据或使用独立事务。测试不得依赖执行顺序，不得共享会被修改的静态实体。

固定测试夹具至少包括：一个可用用户、一个禁用用户、一个可用商家、一个暂停商家、一个营业店铺、一个关闭店铺、一个在售商品、一个下架商品、一个库存不足商品、一个有商品引用的分类和一组待支付订单。

## 9. 覆盖率与交付门槛

- 核心 HTTP 接口覆盖率目标 100%。
- 关键 Service 方法覆盖率不低于 90%。
- 正常、异常、边界和权限场景必须都有断言。
- 后端 `./mvnw test` 和前端 `npm run test:run` 全部通过后才能提交阶段成果。
- JaCoCo、Vitest 覆盖率、失败与通过日志、测试类和需求迭代回归记录统一归档到本目录对应子目录。
- 任何跳过、无断言或失败测试都阻断交付，直到修复或明确更新需求与测试。

## 10. 失败证据和回归记录格式

每个功能保留一条简短记录：

```text
功能/接口：
需求或变更编号：
测试提交：
首次运行：失败（日期、命令、失败摘要、日志路径）
实现提交：
再次运行：通过（日期、命令、结果路径）
重构提交：
回归范围：
最终结果：
```

测试计划只定义预期行为；实际日期、提交号、日志和覆盖率在开发完成后填写。
