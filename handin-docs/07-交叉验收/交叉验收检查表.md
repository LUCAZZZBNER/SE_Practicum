# 轻量级外卖服务平台交叉验收检查表

## 1. 使用说明

本表在设计阶段确定验收口径，第 3 周由交叉验收小组执行。验收时为每项填写“通过、未通过、不适用”，记录证据路径和问题编号。不得在设计阶段预填实际结果。

建议验收环境使用独立测试数据库和专用账号，先记录版本号、提交号、运行命令和环境信息，再执行功能与接口检查。

## 2. 环境与交付检查

- [ ] 能够按照项目说明启动前端、后端和 MySQL。
- [ ] 数据库迁移可在空数据库完整执行。
- [ ] 配置中没有提交真实数据库密码、令牌密钥或个人隐私数据。
- [ ] 项目说明、架构设计、接口设计、数据库设计和测试计划齐全。
- [ ] 测试类、测试日志、覆盖率报告、回归记录、需求迭代记录和开发日志齐全。
- [ ] Git 历史能够体现持续提交和测试先于对应实现。

## 3. REST 接口规范

- [ ] 所有业务接口使用 `/api/v1` 前缀。
- [ ] URI 以资源名词为主，查询使用 GET，创建使用 POST，局部修改使用 PATCH，删除使用 DELETE。
- [ ] 取消订单使用明确业务动作 `POST /orders/{orderId}/cancel`。
- [ ] 分页、过滤和排序通过 Query 参数传递。
- [ ] 创建资源返回 201，普通成功返回 200。
- [ ] 参数错误、未认证、无权限、不存在和冲突分别使用合理 HTTP 状态。
- [ ] 所有成功和失败响应都包含 `code`、`msg`、`data`。
- [ ] 分页响应包含 `items`、`page`、`pageSize`、`total`、`totalPages`。
- [ ] 非法排序、状态、页码、页大小和未知 Body 字段会被拒绝。

## 4. 身份与权限

- [ ] 普通用户与商家分别注册、登录并获得相应角色。
- [ ] 密码以哈希保存，接口响应不返回密码或哈希。
- [ ] 缺少、无效和过期令牌不能访问受保护接口。
- [ ] 用户令牌不能调用商家接口，商家令牌不能调用用户接口。
- [ ] 禁用用户和暂停商家不能继续执行受状态保护的业务。
- [ ] 商家只能维护自己名下的店铺、分类和商品。
- [ ] 用户只能修改自己的购物车、查看和取消自己的订单。
- [ ] 商家只能查看自己店铺的订单。

## 5. 基础功能

### 5.1 用户与商家

- [ ] 用户注册校验账号唯一和两次密码一致。
- [ ] 商家使用独立账号完成注册和登录。
- [ ] 正确凭据登录成功，错误凭据返回统一错误。
- [ ] 用户和商家能够查询、修改自己的资料。
- [ ] 空 PATCH 和空白必填字段被拒绝。

### 5.2 店铺

- [ ] 商家可以创建多个店铺，新店铺默认为关闭。
- [ ] 同一商家不能创建重名店铺。
- [ ] 商家可以设置营业、关闭和临时闭店。
- [ ] 公开列表只显示营业且未删除店铺，支持关键字、分页和排序。
- [ ] 商家能够筛选自己名下不同状态的店铺。

### 5.3 分类与商品

- [ ] 商家能够创建、排序和修改本店分类。
- [ ] 有商品引用的分类不能删除，无引用分类逻辑删除成功。
- [ ] 商家能够创建商品并维护分类、名称、说明、价格、库存和状态。
- [ ] 新商品默认下架，公开查询不显示下架商品。
- [ ] 分类跨店铺使用、负库存、非法价格和非法状态被拒绝。
- [ ] 商品更新要求正确版本，成功后版本增加。

### 5.4 购物车

- [ ] 用户可以添加营业店铺的在售商品。
- [ ] 重复添加同一商品合并数量，不产生重复条目。
- [ ] 数量必须为正且不能超过库存。
- [ ] 购物车展示当前价格、库存、版本、小计、总额和可用状态。
- [ ] 店铺关闭、商品下架或库存减少后，已有条目正确显示不可用原因。
- [ ] 用户可以修改和删除自己的条目，不能操作他人条目。

### 5.5 订单

- [ ] 创建订单要求幂等键、购物车条目和确认的商品版本。
- [ ] 一次订单只包含一个店铺；混合店铺被拒绝。
- [ ] 下单检查店铺营业、商品在售、版本和库存。
- [ ] 下单成功保存店铺、商品名称和成交价格快照。
- [ ] 下单成功扣减库存并清除已结算的购物车条目。
- [ ] 同一幂等键与相同请求不重复建单或扣库存。
- [ ] 同一幂等键与不同请求返回冲突。
- [ ] 用户订单列表和详情支持归属、状态、分页与排序检查。
- [ ] 待支付订单可取消并恢复库存，其他状态不能取消。
- [ ] 商家能够按店铺和状态查看自己的订单。

## 6. TDD 与测试质量

- [ ] 每项核心功能有测试先失败、实现后通过的日志或提交证据。
- [ ] 测试覆盖正常、失败、边界和权限场景，并包含有效断言。
- [ ] 核心接口覆盖率达到 100%。
- [ ] 关键业务方法覆盖率不低于 90%。
- [ ] 所有自动化测试通过，无跳过和无断言测试。
- [ ] 需求变化后新增对应测试并执行原功能回归。
- [ ] DAO 集成测试验证关键约束、映射、版本更新和库存条件更新。
- [ ] 前端测试覆盖路由守卫、请求封装和关键交互组件。

## 7. 架构与代码质量

- [ ] Controller 只处理 HTTP 和参数校验，不包含复杂业务逻辑。
- [ ] 业务规则和事务位于 Service 实现。
- [ ] DAO 只负责持久化，SQL 使用参数绑定。
- [ ] 模块之间通过公开 Service 和 DTO 协作，不跨模块调用 DAO。
- [ ] 全局异常处理和统一返回结构没有在各控制器重复实现。
- [ ] 订单创建和取消具备完整事务边界。
- [ ] 商品版本和原子库存更新能处理并发冲突。
- [ ] 命名、注释和代码结构清楚，没有与三周实践规模不符的过度设计。

## 8. 需求变化适配

- [ ] 每项第二阶段变更有独立编号和原规则、新规则说明。
- [ ] 影响分析覆盖页面、接口、模块、数据表、权限和测试。
- [ ] 变更前先更新设计和测试，变更后保留回归证据。
- [ ] 原接口没有无说明的破坏性变化。
- [ ] 实现需求变化时没有发生不必要的大面积重构。

## 9. 问题记录格式

```text
问题编号：
检查项：
严重程度：阻断 / 严重 / 一般 / 建议
复现环境与版本：
前置条件：
操作步骤：
预期结果：
实际结果：
证据路径：
责任模块：
修复提交：
回归结果：
```

阻断问题包括项目无法启动、数据库无法迁移、核心流程不可用或测试套件无法运行。严重问题包括越权、库存或金额错误、订单重复创建、事务不一致等。所有问题修复后必须由验收人员按原步骤回归。

## 10. 验收结论格式

验收结束后单独形成结论，至少记录：验收日期、双方小组、版本提交号、环境、通过项数量、未通过项数量、问题清单、回归状态和最终结论。结论必须引用实际日志或截图，不以口头说明代替证据。
