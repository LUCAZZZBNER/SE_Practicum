# 轻量级外卖服务平台项目说明

## 1. 项目概况

本项目是《软件工程综合实践》课程的三周实践项目，项目周期为 2026 年 8 月 31 日至 9 月 20 日。项目建设一套轻量级外卖服务平台，为普通用户提供店铺浏览、商品选购、购物车和订单服务，为商家提供店铺、分类、商品和订单管理能力。

项目采用前后端分离方式开发。前端负责页面呈现、交互和接口调用，后端负责身份校验、业务规则和数据持久化。开发过程执行测试驱动开发，先定义可验证的接口行为并编写测试，再完成最小实现，最后在测试保护下重构。

## 2. 建设目标

本项目的主要目标如下：

1. 完成用户、商家、店铺、商品、购物车和订单六个基本业务领域。
2. 使用统一、可测试的 REST 接口建立稳定的前后端契约。
3. 通过清晰的模块和分层降低业务耦合，使第二阶段需求变化能够局部实现。
4. 留存测试失败、实现通过和回归测试等过程证据，体现完整的 TDD 开发过程。
5. 形成可供其他小组直接检查和复现的项目文档及验收材料。

## 3. 用户与使用场景

### 3.1 普通用户

普通用户注册并登录后，可以维护个人资料，浏览店铺、分类和在售商品，将商品加入购物车并调整数量。结算时，用户选择同一店铺的购物车条目创建订单；订单创建成功后，系统扣减库存并清除已结算的购物车条目。用户可以查看自己的订单列表和详情，并取消仍处于待支付状态的订单。

### 3.2 商家

商家拥有独立账号。商家注册并登录后，可以维护商家资料，创建一个或多个店铺，设置店铺营业、关闭或临时闭店状态，管理本店分类、商品、价格、库存和上下架状态，并查看所属店铺的订单。

### 3.3 交叉验收人员

验收人员按照统一检查表验证功能、接口语义、权限、异常返回、分页查询和测试材料。验收只使用公开操作入口和可交付证据，不依赖开发成员的口头补充才能完成基本判断。

## 4. 功能范围

### 4.1 用户模块

- 普通用户注册、登录、查询个人资料和修改个人资料。
- 用户账号分为 `ACTIVE` 和 `DISABLED`；禁用账号不能登录或进行需校验账号状态的业务操作。
- 注册时校验两次密码一致，密码只以哈希形式保存。

### 4.2 商家模块

- 商家注册、登录、查询商家资料和修改商家资料。
- 商家账号分为 `ACTIVE` 和 `SUSPENDED`；暂停账号不能进入受保护的商家业务。
- 普通用户和商家使用相互独立的账号体系及角色。

### 4.3 店铺模块

- 商家创建和维护自己的店铺；同一商家下店铺名称不能重复。
- 店铺状态包括 `OPEN`、`CLOSED` 和 `TEMPORARILY_CLOSED`，新建店铺默认为关闭。
- 访客可以分页浏览店铺和查看店铺详情；登录商家可以筛选自己名下的店铺。

### 4.4 分类与商品模块

- 商家为自己的店铺创建、排序、修改和删除商品分类。
- 已被商品使用的分类不能删除，分类删除采用逻辑删除。
- 商家创建和修改商品，维护分类、名称、说明、价格、库存及上下架状态。
- 新建商品默认为 `OFF_SALE`，商品状态可切换为 `ON_SALE`。
- 商品更新使用版本号进行并发控制；价格或版本变化时，旧版本不能继续结算。
- 普通访客只看到在售商品；商家可查看自己店铺的下架商品。

### 4.5 购物车模块

- 普通用户可以加入商品、查看购物车、修改数量和删除条目。
- 同一商品重复加入时合并数量，同一用户与商品只保留一条购物车记录。
- 加入或修改数量时校验店铺营业状态、商品上下架状态和库存。
- 购物车展示当前价格、库存、版本和可用性，并根据当前商品价格计算小计与总额。

### 4.6 订单模块

- 用户选择购物车条目创建订单，一次结算只能包含一个店铺的商品。
- 创建订单必须携带幂等键和客户端确认的商品版本；相同用户、相同幂等键和相同请求返回原订单，不重复扣减库存。
- 订单保存店铺名称、商品名称和成交单价快照，后续店铺或商品修改不影响历史订单。
- 订单状态包括 `PENDING_PAYMENT`、`PAID`、`PREPARING`、`DELIVERING`、`COMPLETED` 和 `CANCELLED`。本阶段新订单进入待支付状态，仅待支付订单允许由所属用户取消；取消后恢复库存。
- 用户只能查看和取消自己的订单，商家只能查看自己店铺的订单。

## 5. 非功能要求

### 5.1 正确性与一致性

- 所有接口使用统一的 `code`、`msg`、`data` 返回结构。
- 订单创建、库存扣减、订单明细写入和购物车清理在同一业务事务中完成。
- 数据库使用外键、唯一约束、检查约束和应用层校验共同保护数据一致性。

### 5.2 安全性

- 受保护接口要求有效身份令牌，并区分 `USER` 与 `MERCHANT` 两种角色。
- 服务层再次检查账号状态和资源归属，不能只依赖页面入口隐藏功能。
- 密码不明文保存，内部异常不向客户端暴露堆栈和数据库信息。

### 5.3 可维护性

- 后端按业务领域组织代码，每个领域保持 Controller、Service、DAO、Entity 的职责边界。
- 跨模块业务通过公开 Service 接口和数据对象协作，不直接操作其他模块的数据访问层。
- 数据库结构使用版本化迁移管理，接口使用 `/api/v1` 进行版本隔离。

### 5.4 性能与容量

- 店铺、商品和订单列表使用分页，默认每页 10 条，单页最多 100 条。
- 高频筛选字段建立组合索引；库存扣减在数据库中使用带条件的原子更新。
- 本项目按课程实践规模设计，不引入分布式服务、消息队列或缓存集群。

### 5.5 可测试性

- 控制器测试覆盖 HTTP 方法、路径、状态码、返回结构、参数校验和权限。
- 服务测试覆盖正常、异常、边界、资源归属、事务一致性和并发冲突。
- 核心业务接口覆盖率目标为 100%，关键业务方法覆盖率不低于 90%，所有测试必须通过后才能合并功能代码。

## 6. 技术方案

| 层次 | 主要技术 | 用途 |
| --- | --- | --- |
| 前端 | Vue 3、Vue Router、Element Plus、Axios、Vite | 页面、路由、交互和 HTTP 请求 |
| 前端测试 | Vitest、Vue Test Utils、jsdom | 组件、路由守卫和请求封装测试 |
| 后端 | Java 17、Spring Boot、Spring MVC | REST 接口和业务服务 |
| 数据访问 | MyBatis、Flyway | SQL 映射和数据库版本迁移 |
| 数据库 | MySQL 8 | 业务数据持久化 |
| 后端测试 | JUnit 5、MockMvc、JaCoCo | 单元、接口、集成与覆盖率测试 |
| 版本管理 | Git | 分支协作和 TDD 过程留痕 |

## 7. 阶段安排

| 阶段 | 主要工作 | 阶段出口 |
| --- | --- | --- |
| 第 1 周：基础实现 | 完成设计基线、六个基础模块、测试用例和接口联调 | 基础功能可运行，测试全部通过，过程材料齐全 |
| 第 2 周：需求迭代 | 记录需求变更，完成影响分析，先补测试再修改实现 | 新旧测试全部通过，原功能没有回归缺陷 |
| 第 3 周：完善验收 | 重构、完善交互和异常提示，执行全量测试与交叉验收 | 文档、代码、测试报告和验收记录完整 |

## 8. 完成标准

项目达到以下条件时视为完成基础交付：

1. 用户、店铺、商品、购物车和基础订单流程能够正常使用，商家管理功能能够支持上述流程。
2. 接口路径、HTTP 方法、状态码、分页和鉴权符合项目约定。
3. 正常、失败、边界和权限场景均有有效断言，完整测试套件通过率为 100%。
4. 需求变化有独立记录，变更后完成原功能回归测试。
5. 项目说明、架构设计、数据库设计、测试材料、迭代记录、团队日志和验收材料齐全。
