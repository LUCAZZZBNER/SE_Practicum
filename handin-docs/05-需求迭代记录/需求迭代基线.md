# 轻量级外卖服务平台需求迭代基线

## 1. 基线目的

本基线确定第 1 周开始编码前已经达成一致的功能、接口行为和质量要求。第 2 周出现新增或调整需求时，以本文件判断影响范围，先修改测试和设计，再修改实现，避免把需求变化混入原始范围。

基线建立日期为 2026 年 8 月 31 日，适用接口版本为 `/api/v1`。

## 2. 功能需求基线

| 编号 | 模块 | 基线需求 | 验收要点 |
| --- | --- | --- | --- |
| U-01 | 用户 | 普通用户能够注册，账号唯一，两次密码一致 | 成功返回 201；重复账号和密码不一致有稳定错误 |
| U-02 | 用户 | 普通用户能够登录并获得带角色的访问令牌 | 错误凭据、禁用账号不能登录 |
| U-03 | 用户 | 用户能够查询和修改自己的昵称、电话 | 不能通过请求指定其他用户编号 |
| M-01 | 商家 | 商家使用独立账号注册、登录和维护资料 | 商家与用户角色隔离，暂停商家不能操作业务 |
| S-01 | 店铺 | 商家能够创建多个店铺并维护名称、说明和状态 | 新店默认关闭，同商家店名唯一，仅所有者可修改 |
| S-02 | 店铺 | 访客能够分页浏览营业店铺并查看详情 | 公开列表支持关键字、分页和排序，商家本人列表可按状态筛选 |
| I-01 | 分类 | 商家能够创建、排序、修改和删除本店分类 | 店内分类名唯一，有商品时不能删除 |
| I-02 | 商品 | 商家能够创建和维护本店商品、价格、库存和状态 | 新商品默认下架，分类必须属于同店铺 |
| I-03 | 商品 | 用户能够分页浏览在售商品和查看商品详情 | 公开查询不暴露下架商品，商家可查询自有下架商品 |
| I-04 | 商品 | 商品修改和库存预占支持并发冲突识别 | 使用版本号和条件更新，不能出现负库存 |
| C-01 | 购物车 | 用户能够加入商品并合并相同商品数量 | 店铺营业、商品在售且库存充足 |
| C-02 | 购物车 | 用户能够查询、修改和删除自己的购物车条目 | 展示当前价格、可用性、小计和总额 |
| O-01 | 订单 | 用户能够选择同一店铺的购物车条目创建订单 | 校验版本与库存，保存快照、扣库存、清购物车 |
| O-02 | 订单 | 创建订单具有用户维度的幂等性 | 同键同请求返回原订单，同键不同请求返回冲突 |
| O-03 | 订单 | 用户能够查询自己的订单列表和详情 | 支持状态、分页和排序，不能读取他人订单 |
| O-04 | 订单 | 用户能够取消自己的待支付订单 | 状态改为取消并恢复库存，不能重复取消 |
| O-05 | 订单 | 商家能够查询自己店铺的订单 | 可按店铺和状态筛选，不能查看其他商家订单 |

## 3. 接口与数据基线

- 所有接口位于 `/api/v1`，统一返回 `code`、`msg`、`data`。
- 列表通过 Query 参数分页、筛选和排序；默认第 1 页，每页 10 条，最大 100 条。
- 身份分为 `USER` 和 `MERCHANT`，受保护接口使用 Bearer 令牌。
- 核心数据表为 `users`、`merchants`、`shops`、`product_categories`、`products`、`cart_items`、`orders`、`order_items`。
- 用户、商家、店铺、商品和订单状态值由接口设计和数据库检查约束共同固定。
- 商品 `version`、订单 `idempotency_key` 与 `request_fingerprint` 属于基线一致性机制，不是后续可随意删除的实现细节。

详细路径、请求和错误码以接口设计为准，字段、约束和索引以数据库设计为准。

## 4. 质量基线

1. 所有新行为先有失败测试，再写最小实现，最后执行重构和完整回归。
2. 核心接口覆盖率达到 100%，关键业务方法覆盖率不低于 90%。
3. 正常、失败、边界和权限用例必须有明确断言。
4. Controller、Service、DAO、Entity 职责清楚，模块之间只通过 Service 接口和 DTO 协作。
5. 完整测试套件通过率为 100%，不得以跳过测试代替修复。
6. 测试类、失败与成功日志、覆盖率报告、回归记录和 Git 提交历史均须留存。

## 5. 变更处理流程

收到新需求后按以下顺序处理：

1. 为变更建立编号，写清原规则、新规则、原因和验收条件。
2. 对照本基线确认新增、修改、废弃和保持不变的行为。
3. 分析受影响的页面、接口、Service、数据库、权限和已有测试。
4. 若接口或数据结构变化，先修订设计文档并说明兼容策略。
5. 先增加或调整测试并保留失败证据，再修改实现。
6. 运行变更相关测试和完整回归，记录结果及遗留问题。
7. 评审通过后合并；不得直接覆盖基线或删除原测试证据。

## 6. 单项变更记录格式

后续每项变更使用独立文件，文件名采用 `变更编号-简要名称.md`，内容包括：

```text
变更编号与日期：
提出人：
原规则：
新规则：
变更原因：
验收条件：
影响页面与接口：
影响模块与数据表：
兼容性与迁移方案：
新增或调整的测试：
首次失败测试证据：
实现提交：
回归范围与结果：
评审结论：
```

没有发生变化的模块也应在影响分析中明确说明，便于评审者判断分析是否完整。

## 7. 基线变更规则

初始需求基线一经进入编码阶段不直接改写。表述错误可以通过单独勘误记录修正；业务含义变化必须建立需求变更记录。若发生破坏兼容性的接口调整，保留 `/api/v1` 或建立新版本，并为旧行为保留回归测试直至兼容期结束。
